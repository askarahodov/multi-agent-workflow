# Ротация истории и экономный контекст внешнего QA (v1, к реализации)

**Дата:** 2026-10-13. **Цель:** не кормить ChatGPT старыми закрытыми задачами и длинными transcript-файлами, сохранив полный Git-аудит и exactly-once обмен.

> Внедрение НЕ активировано только публикацией этого файла. Не сокращать действующие `requests.md`/`responses.md`, пока не обновлены оба участника протокола и не выполнена миграционная приёмка. Источник истины для задач — локальный Kanban. Эта ветка никогда не вливается в `main`.

## Что читать каждый цикл

При нормальном режиме внешний QA читает **ТОЛЬКО**:

1. `status/current.md` — один свежий фактический snapshot (либо `QA_DASHBOARD.md` для пользователя, без повторного копирования данных).
2. `index/current.md` — **короткая очередь** новых/требующих проверки запросов и открытых QA-дефектов, с SHA исходных коммитов, статусом и ссылками на первичные доказательства.
3. **Только указанные в индексе** файлы по `path` — при наличии нового вопроса или нехватке доказательств.

Без нового ревью не загружать целиком `responses.md`, `requests.md`, старые QA-отчёты, все diff и архивы. Локальный сбор состояния и дедуп делать обычным Python без LLM.

## Файлы и права

| Путь относительно `.coordination/external-qa/` | Пишет | Содержимое |
|---|---|---|
| `status/current.md` | координатор | Последний проверенный snapshot |
| `QA_DASHBOARD.md` | координатор | Русская читаемая сводка из того же snapshot |
| `index/current.md` | координатор | Компактная очередь и активные риски, **не история** |
| `requests.md` | координатор | Текущие запросы, ожидающие QA, + короткий недавний хвост |
| `responses.md` | внешний QA | Новые ответы, ожидающие обработки координатором, + короткий недавний хвост |
| `archive/YYYY-MM/requests-0001.md` | координатор | Неизменяемые закрытые/доставленные блоки QA-REQ |
| `archive/YYYY-MM/responses-0001.md` | внешний QA | Неизменяемые подтверждённые блоки QA-RSP |
| `archive/manifest.md` или компактный машинный `archive/manifest.json` | строго разграниченные авторы по своим записям; безопаснее отдельные `archive/requests-index.json` и `archive/responses-index.json` | Стабильные ID → путь, sha256, дата, тип, итог; без содержимого переписки |
| `cases/QA-CAS-*.md` | координатор создаёт из открытой Kanban-задачи, внешний QA ссылается в ответе (без перезаписи case) | Короткое описание **незакрытого** дефекта, текущий статус, ID задач, критерий закрытия |

Если один файл требует двух авторов, **разделить по владельцу**, не допускать совместной записи. Каталоги `archive` — история для ручного аудита, не вход в каждый cron/LLM цикл.

## Формат компактного index/current.md

```md
# Активные вопросы QA
- snapshot_id: UTC-...
- generated_at_utc: ...
- status_source: status/current.md @ <Git commit>
- main_sha: <SHA>
- inbox_revision: <SHA>
- total_unanswered: 1
- total_open_cases: 2
- retention_version: 1

## Новые QA-запросы (только без независимого ответа)
| req_id | priority | kind | task_id | evidence_path/ref | received_commit |
|---|---|---|---|---|---|
| QA-REQ-... | P1 | REVIEW_REQUEST | t_... | path/sha | ... |

## Открытые вопросы/блокеры (не весь transcript)
| case_id | owner | task_id | verdict | next_action | evidence_ref |
|---|---|---|---|---|---|
| QA-CAS-... | sdlc-reviewer | t_... | BLOCKED | published diff | ... |

## Недавно решено
- QA-CAS-... → VERIFIED/PASS @ <SHA>, archived: <path>
```

Не включать сюда ACK_ONLY, старые PASS, полностью закрытые задачи без изменений, старые логи или списки всех 175 `done`. Для `OPEN` показывать задачу до evidence-verified закрытия; если она долго открыта, короткая строка в индексе + детали в `cases/`.

**Дедуп:** индексировать `QA-REQ-` по ID и типу (`ACK` vs `REVIEW_REQUEST`), а не по содержимому тела или просто старому SHA. Технические ACK на QA-RSP — не новый ревью-запрос. `QA-RSP-` удаляется из активного inbox только после remote ACK; исходный дефект может остаться отдельным OPEN case до независимой проверки.

## Политика ротации

- **Период:** раз в сутки и/или при достижении **32 KiB** активного файла или **30** завершённых записей. Каждый `requests.md`/`responses.md` обрабатывает **только его владелец**.
- **Никогда не архивировать без подтверждения доставки**: `QA-RSP` → должен существовать `in_reply_to` в удалённом `requests.md`; `QA-REQ` с `kind=REVIEW_REQUEST` → должен существовать `request: QA-REQ-...` в удалённом `responses.md`, либо явно зафиксирован `CANCELLED` владельцем.
- `ACK` на уже обработанный `QA-RSP` можно архивировать после сверки remote/ledger. Это подтверждение доставки, **не закрытие исходной рекомендации**.
- На каждый перемещаемый блок сохранять **точное исходное Markdown-содержимое**, ID, `sha256` и путь в immutable shard. В активном индексе оставлять ссылку на case, если проблема не закрыта.
- В одном fast-forward Git commit: создать архивный shard и его owner-index, затем удалить архивированные блоки из owner-active файла. До commit/push сделать консистентную проверку всех блоков и хешей.
- Если параллельно обновились QA и координатор: fresh fetch, rebase/replay только своих файлов, **без force-push**, заново проверить ack/response перед удалением. При конфликте/ошибке ротацию отменить, файлы оставить в прежнем состоянии.
- После push проверить `git ls-remote`, existence/archive digest, количество неизменённых активных ID и взаимные ссылки через **удалённый** GitHub API.
- Не пытаться обрезать файл поверх неполученных новых сообщений, не терять `requests.md` ACK-историю до завершения миграции дедуп.
- Не создавать новые shards при каждом cron tick: ротация — **событие** при пороге, без LLM-вызова. Для роста более 32 KiB по активным **открытым** вопросам не удалять их: разбить подробности на cases и оставить короткий индекс.

## Безопасный cutover

1. **Подготовка:** локально и в GitHub сравнить все существующие QA-REQ/QA-RSP ID; вычислить все связи `in_reply_to`, `request`, `verdict`. Зафиксировать перед миграцией число блоков, sha256, списки непрочитанных ID.
2. Координатор поддерживает **архивный дедуп**: после сокращения `requests.md` повторный ACK не должен появиться даже при потере локальной SQLite-БД. Восстановление должно считывать компактный архивный index/ledger и текущий requests. Проверить 3 цикла и изменённый body.
3. Внешний QA поддерживает чтение `index/current.md` и адресную загрузку блоков. Не полагаться на то, что удалённые старые `responses.md` содержат все исторические вердикты.
4. Сначала создать индексы/архивы **без удаления**. Проверить digest, ID и ссылки. Потом отдельными транзакциями по owner сократить активные файлы. Никогда не сокращать два owner-файла в одной авторской операции.
5. Прогнать acceptance tests (см. ниже). В случае провала вернуть активные файлы из архивов обычным новым commit без force.

## Приёмка

- Индекс соответствует последнему `status/current.md`, включает все новые `REVIEW_REQUEST` и все **незакрытые cases**, но не содержит десятков закрытых PASS/ACK.
- На каждом миграционном шаге количество уникальных ID в (active + archive) **не уменьшается**, hash каждого перенесённого блока совпадает.
- Аварийный рестарт после архивации, но до push; 2 параллельных автора; сетевой сбой; повторная попытка: нет потери и дубликатов.
- Удалённый `QA-RSP`, который был ACK-нут и затем архивирован, **не ACK-ается повторно** при изменённом теле/восстановлении ledger.
- Новое неотвеченное сообщение остаётся активным, даже если порог достигнут; читается и получает ответ.
- Три пустых прохода: 0 commit/push/LLM; новый статус Kanban меняет только snapshot/index/dashboard.
- Сравнить объём токенов прежнего и нового входа **на фиксированном сценарии**; цель — не более нескольких KiB на пустую проверку, исторические файлы не загружаются.
- Проверить ссылки после публикации и синхронность русского Dashboard.

**Важно:** текущая версия `qa-sync` читает весь `responses.md` обычным Python и dedup по remote `requests.md` ∪ SQLite. Это **не тратит LLM-токены**, но при ротации `requests.md` потребуется расширить восстановление состояния из archive index. Само внедрение ротации поручено координатору (owner запросов и локального cron); внешний QA имеет право архивировать **только свои ответы** после совместной успешной миграционной приёмки.
