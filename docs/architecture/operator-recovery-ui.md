# Операторский интерфейс аварийного восстановления (Issue #38)

Раздел **«Аварийное восстановление»** доступен из бокового меню
Multi-Agent Platform. Это защищённая административная поверхность для
проверки прерванных попыток — не интерфейс повторного запуска агента.

## Что доступно

1. Список задач, переведённых сервером в карантин после прерванного
   выполнения: `GET /api/v1/admin/recovery-quarantine`.
2. Последнее подтверждение оператора:
   `GET /api/v1/admin/tasks/{task_id}/reconciliation`.
3. Реальные **обезличенные** состояния файловых инструментов,
   `CLAIMED / SUCCEEDED / DENIED`, только из доверенного
   read-only Tool Ledger:
   `GET /api/v1/admin/tasks/{task_id}/tool-ledger`.
4. Ручная фиксация решения:
   `POST /api/v1/admin/tasks/{task_id}/reconciliation`.
   `UNKNOWN` фиксирует неопределённость;
   `CONFIRMED_SIDE_EFFECT` и `CONFIRMED_NO_SIDE_EFFECT` требуют
   проверки доказательства сервером и предварительного просмотра журнала
   в интерфейсе. Для любого решения требуются идентификатор доказательства,
   64-символьный SHA-256 и явное подтверждение оператора.

**Никакой кнопки «повторить», `claim_task`, `retry` или запуска
инструмента здесь нет.** Даже подтверждённый исход оставляет старую
задачу в статусе `blocked`. Для продолжения требуется отдельное
создание новой работы после внешней проверки артефактов.

## Режимы и отказоустойчивость

- Frontend использует **существующий** `ApiAdapter` и настройки
  аутентификации, отдельные браузерные ключи не добавляются.
- При HTTP 401/403 выводится сообщение о необходимости доступа
  администратора; нет обхода прав или автоматической повторной отправки.
- Если Tool Ledger не настроен (503), интерфейс допускает только
  `UNKNOWN`. **Backend применяет тот же запрет:** прямой административный
  `POST /api/v1/admin/tasks/{task_id}/reconciliation` с
  `CONFIRMED_*` отклоняется при отсутствии доверенного Ledger (503).
  Перед подтверждением сервер проверяет доступность ledger для всех
  прерванных попыток данной quarantined task; сломанный журнал приводит
  к отказу без записи решения. `UNKNOWN` доступен без Ledger.
  `NO_RECORDS` не означает, что side effects отсутствуют: решение
  подтверждается человеком после независимой проверки фактов и доказательств.
- Все HTTP-запросы запускаются по выбору пользователя или при открытии
  раздела; фонового polling и модельных запросов нет.
- Offline `MockAdapter` не симулирует админские решения и всегда
  отклоняет запись. Для настоящей сверки требуется действующий backend
  и роль admin.
- В режиме Vite запросы `/api/v1/admin` маршрутизируются в
  `ORCH_UPSTREAM`, как другие endpoint orchestration-server.

## Принятие

```bash
cd frontend
npm ci
npm run typecheck
npm run test:run
npm run build
```

Компонентные регрессии проверяют явное подтверждение,
`CLAIMED`-предупреждение, недоступность журнала, неизменяемое
подтверждённое решение, RBAC 403 и отсутствие вызова
`claimTask`/`submitTask`.

**За пределами этапа:** production RBAC/SSO конфигурация, работа с
удалённым Tool Ledger, хранение и версия доказательств, контролируемое
создание новой задачи и полноценный workflow reconciliation (#38).


## Проверка проекта, согласованности и неопределённого POST

Операторская страница теперь привязана к **текущему проекту, запуску и API-адаптеру**. При выбранном запуске UI предварительно читает серверный run и проверяет `project_id` до получения списка карантина. В административном списке без выбранного запуска все parent runs проверяются через backend (не более пяти параллельно); чужие проекту задачи не отображаются. Некорректные/отсутствующие parent-run ID, неожиданный статус задачи либо HTTP-ошибка не разрешают фиксацию решения. Смена A → B → A или API-адаптера размонтирует старую область; запоздавшие ответы списка/доказательств не меняют новый экран.

Перед разрешением POST **обязателен успешный GET текущей аттестации** (валидная запись или 404 «записи нет»). HTTP 401/403/503 и противоречащий task ID блокируют новую запись; ошибка Tool Ledger блокирует решения `CONFIRMED_*`, но не `UNKNOWN`. Журнал и подтверждённое решение проверяются на совпадение task ID и структурную целостность. При сохранении оператор должен явно отметить обзор, доказательство и SHA-256. Ответ POST должен повторять тот же task ID, решение, ссылку и digest, иначе результат считается неопределённым; **положительное уведомление не выводится**.

На период отправки и после потери HTTP-ответа повторная отправка для этой задачи блокируется. Блокировка сохраняется в ограниченном sessionStorage текущей вкладки и снимается **только при достоверном повторном чтении сохранённого решения с сервера**, но не по одному 404 (последний не доказывает, что предыдущий POST не будет зафиксирован позже). Поздний ответ старой задачи/проекта не меняет текущую форму. Никакого автоматического повторного POST, claim, retry, resume или создания новой задачи не выполняется. Backend по-прежнему независимо проверяет ADMIN RBAC, фактические bytes доказательства и ledger перед записью и оставляет задачу blocked. В CI: отрицательные тесты 403/неверного ledger, чужого проекта, A → B → A, потерянного ответа, неизменяемости решения и повторного чтения; Compose Chromium проверяет read-only run-centric recovery на настоящем API. Операторская аттестация требует отдельно настроенного доверенного evidence root и **не** симулируется платным AI.
