# Fail-closed recovery of interrupted native execution (#36)

## Почему это важно

До этой правки `OrchestrationEngine.recover()` автоматически переводил
`in_progress` задачу в `pending`. Но файловый инструмент мог уже
записать изменения до аварии. Новый LLM-запрос после рестарта может
сгенерировать новый `tool_call_id` — SQLite ledger #27 не может
обнаружить семантически повторённое действие с новым ID.

## Новое поведение по умолчанию

При старте orchestration-server (`recover_on_startup=True`):

- Незавершённый `TaskAttempt` получает статус `interrupted`.
- Соответствующая задача помечается `blocked`, а **не** `pending`.
- `retry_at` очищается; исходная задача **не** выполняется повторно.
- Ранее занятые агенты переходят из `busy` в `inactive`, **не** в
  `idle`: внешний процесс worker мог пережить рестарт API-сервера.
  `claim_task` разрешает только `idle`, поэтому прежний agent ID
  нельзя немедленно назначить другой задаче.
- `SagaEvent=task.recovery_quarantined` фиксирует постоянную обезличенную
  причину `interrupted_attempt_requires_reconciliation`.
- `completed` задачи и unrelated pending задачи не затрагиваются.
- Повторный recover идемпотентен и не создаёт ещё один переход.

**Ручной** `POST /api/v1/admin/recover` временно возвращает HTTP **409**
даже администратору: в продукте ещё нет достоверной проверки остановки
внешних worker и durable generation/lease fencing. Проверки «нет running
в БД» недостаточно из-за гонки с новым `claim`. Это осознанный
fail-closed режим до отдельной реализации quiescence/fencing в #38/#33.
Нельзя вручную менять `inactive` на `idle` или обходить quarantine:
вместо этого после проверки фактической остановки старых исполнителей и
их побочных эффектов выделяется **новая** управляемая worker identity.

**Ограничение:** такая мера предотвращает повторное назначение прежнего
agent ID, но не может отменить уже исполняющийся `runner` и не доказывает
отсутствие поздних файловых/сетевых side effects. До внедрения fencing
нельзя считать unattended recovery и `CONFIRMED_NO_SIDE_EFFECT`
производственно безопасными на основе только статуса в БД.

## Действия оператора

1. Проверить последние `CLAIMED`/`SUCCEEDED` tool IDs в **защищённом**
   журнале вне workspace, журналы gateway и фактические артефакты.
2. Выяснить, произошли ли side effects до аварии; повторная генерация
   нового tool ID не доказывает отсутствие дублей.
3. Создать **новую** проверенную task/run для остатка работы только после
   reconciliation, с новым workspace/политиками/лимитами.
4. Не снимать карантин массово и не делать скрытый auto-retry.

Этот срез **не реализует** полноценный UI ручной reconciliation, отдельный
production worker daemon или distributed exactly-once. Эти задачи остаются
блокерами #33/#11.

```bash
cd orchestration-server
python -m pytest tests/test_safe_recovery.py -q
```

В CI тесты доказывают quarantine, idempotence, невозможность повторного
назначения `inactive` / `terminated` agent, отказ ручного recover,
отсутствие вызова runner для заблокированной задачи, выполнение
других pending задач на **отдельно зарегистрированном** агенте и
сохранение подтверждённой completed задачи.


## Этап #38: журнал решений администратора

После восстановления администратор может прочитать список quarantined задач:

```text
GET /api/v1/admin/recovery-quarantine
GET /api/v1/admin/tasks/{task_id}/reconciliation
POST /api/v1/admin/tasks/{task_id}/reconciliation
```

Для всех трёх маршрутов требуется роль `admin`; запись недоступна
ключам `read` и `write`. POST принимает:

```json
{
  "decision": "UNKNOWN",
  "evidence_ref": "qa-artifacts/incident-123",
  "evidence_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

`evidence_ref` — безопасный идентификатор сохранённого доказательства,
`evidence_sha256` — SHA-256 контрольная сумма доказательства.
Для подтверждённых решений сервер проверяет **реальные байты** из
доверенного каталога (см. этап 2 ниже), а не только заявление оператора.
Проверка хеша сама по себе не доказывает истинность решения или
отсутствие побочных эффектов. `UNKNOWN` сохраняет блокировку без
обязательного файлового доказательства. Не вставлять ключи, содержимое
файлов или секретные URL в ссылку на доказательство.

Разрешены решения `UNKNOWN`, `CONFIRMED_SIDE_EFFECT`,
`CONFIRMED_NO_SIDE_EFFECT`. Первое можно уточнить одним из двух
подтверждённых. Подтверждённые решения неизменяемы.
Актуальное решение живёт в `task_reconciliations` (одна строка на
задачу), а история — в неизменяемых `task.reconciliation_attested`
событиях SagaEvent. Оператор устанавливается из `AuthContext.subject`,
не из запроса. Конкурирующие попытки подтверждения не могут
создать два успешных решения.

**Любое решение оставляет исходную задачу в `blocked`.**
Система не создаёт новую попытку, не вызывает LLM и не запускает
инструменты. Чтобы выполнить остаток работы, оператор отдельно
создаёт новую workflow task после сопоставления исходных артефактов
и `CLAIMED` ledger-записей.

Для существующей БД необходимо применить новую таблицу
`task_reconciliations` при миграции или `create_all` на старте сервиса.
В production необходимо использовать управляемые SQL-миграции.
Чтение Ledger-статусов, доказательства и UI принятия решения требуют
отдельного этапа — не считать этот API готовым unattended recovery.

```bash
cd orchestration-server
python -m pytest tests/test_reconciliation.py tests/test_reconciliation_api.py -q
```


## Этап 2: проверка SHA-256 по реальному файлу на сервере

Для подтверждённых решений (`CONFIRMED_SIDE_EFFECT` или
`CONFIRMED_NO_SIDE_EFFECT`) теперь **обязательна** настройка:

`ORCH_RECONCILIATION_EVIDENCE_ROOT=/var/lib/multi-agent/reconciliation-evidence`

Сервис открывает выбранный файл под указанным **доверенным**
каталогом, вычисляет SHA-256 из фактических байтов (не верит
переданному клиентом хешу) и сравнивает с указанным в запросе.

Защита: ограничение до 8 МиБ, дескриптор-относительный путь с
`O_NOFOLLOW`, запрет \"..\", symlinks в каждом компоненте, FIFO
и hardlinks. Неверный хеш или небезопасный файл → 422, отсутствие
настройки → 503. По умолчанию никакого произвольного чтения файлов
хоста. На Windows верификатор не включается без безопасной реализации.

Каталог должен принадлежать доверенному сервисному администратору,
быть недоступным для записи агентам и не содержать секретов.
**Все вложенные каталоги на пути к файлу доказательства также должны быть
недоступны для групповой и общей записи** (например, `0750` или `0700`).
Сервер проверяет права уже открытых дескрипторов каталогов **при каждой
верификации**, включая корневой каталог, и отклоняет доказательство,
если каталог имеет `group/world write` даже после изменения прав во время работы сервиса.
Это ограничивает риск подмены доказательства через каталог с ошибочными правами.

Его содержимое формируется **вне агента** и публикуется в
контролируемом workflow. Даже совпадение SHA-256 доказывает лишь
целостность проверенного файла **в момент чтения**; оно не
доказывает правдивость заключения оператора и не запускает задачу
повторно. Решение \"UNKNOWN\" допускается без verifier для фиксации
неопределённости — исходная задача при этом остаётся \"blocked\".

Пример для разработчика:

```bash
install -d -m 0750 /var/lib/multi-agent/reconciliation-evidence
export ORCH_RECONCILIATION_EVIDENCE_ROOT=/var/lib/multi-agent/reconciliation-evidence
```

Регрессионные проверки:

```bash
cd orchestration-server
python -m pytest tests/test_reconciliation_evidence.py tests/test_reconciliation_api.py -q
```


## Этап #38: чтение статусов Tool Ledger для карантинных задач

Сервис может показать оператору реальные статусы вызовов из SQLite-журнала,
**только если он находится на доверенном локальном пути**. Подключение
необязательно; оно выключено по умолчанию:

```bash
export ORCH_RECONCILIATION_TOOL_LEDGER_PATH=/var/lib/multi-agent/ledger/tool-claims.sqlite3
```

Директория должна быть защищена от записи недоверенными агентами,
сам файл должен принадлежать процессу сервиса, быть обычным файлом с
правами не шире `0600` и не быть symlink/hardlink.
Промежуточные компоненты пути к ledger проверяются на symlink при создании
reader и перед каждым чтением. Символические ссылки в родительских
каталогах приводят к отказу, даже если непосредственный каталог безопасен.
База открывается
в SQLite `mode=ro` и `query_only`; сервер **не создаёт** её сам.

Только администратор может вызвать:

```text
GET /api/v1/admin/tasks/{task_id}/tool-ledger
```

Сервер получает `run_id` и `attempt_id` из собственной базы и
показывает **только прерванные попытки в настоящем recovery-quarantine**.
Scope формируется в том же виде, что и у текущего нативного worker:
`run-{run_uuid}/attempt-{attempt_uuid}`. Нельзя указать scope или путь
к SQLite в запросе. Возвращаются только статусы
`CLAIMED / SUCCEEDED / DENIED`, тип разрешённого инструмента и
16-символьный fingerprint ID (не исходный `tool_call_id`).
Аргументы, prompt, содержимое файлов, исходные call IDs и полный
путь к БД никогда не включаются в API-ответ. Чтение ограничено
200 строками на попытку и 50 прерванными попытками на задачу.
Читатель проверяет идентификаторы вызовов по контракту доверенного writer:
`[A-Za-z0-9_-]{1,128}`. Все несоответствующие записи отклоняются,
а не учитываются как достоверные доказательства.
Имя инструмента должно быть строкой длиной не более 64 символов, как у
доверенного writer. Некорректный тип или превышение лимита отклоняется;
неизвестное, но корректное имя отображается как `<unsupported>` без раскрытия. Параметр лимита
чтения должен быть целым числом от 1 до 1000; логические значения запрещены.

Если опция не настроена, endpoint возвращает 503. Отсутствие записей
отображается как `NO_RECORDS`, **а не как подтверждение безопасности
повторного запуска**: журналы могли находиться на другом хосте либо
использовать другую версию соглашения о scope. Повреждённая или
недоступная SQLite приводит к отказу, без ложного «чистого» состояния.

**Топологическое ограничение:** этот этап читает лишь локальную,
доверенно смонтированную SQLite worker. При физически удалённом worker
не копировать непроверенные статусы и не давать orchestration-server
доступ на запись в базу агента; потребуется отдельно
аутентифицированный read-only status service с контрактом snapshot.

Просмотр не переводит задачу в `pending` и не выполняет инструменты.
Даже `SUCCEEDED` не доказывает правильность артефакта, а `CLAIMED`
остается неоднозначным до ручной проверки.

```bash
cd orchestration-server
python -m pytest tests/test_tool_ledger_inspection.py -q
```

Дополнительно отдельный CI Native E2E проверяет чтение журнала,
созданного **настоящим** `agent_management.SqliteToolLedger`.
