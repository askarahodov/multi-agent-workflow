# Серверные Lease для Native Agent — этап #33/#38

## Назначение

Lease — краткоживущее **серверное разрешение** на конкретную попытку работы
агента. Оно помогает различать живую/просроченную/отозванную попытку, не
полагаясь на собственное заявление LLM «я ещё выполняю задачу».

Эта стадия — **не полноценное распределённое fencing**. По умолчанию она
выключена, чтобы не ломать существующие локальные/HTTP workers.

## Опциональная конфигурация

- `ORCH_ATTEMPT_LEASE_ENABLED=0` (по умолчанию). Для тестовых доверенных
  исполнителей: `1`.
- `ORCH_ATTEMPT_LEASE_TTL_SECONDS=60` (разрешено 5–300 секунд).
- Доступ к API — только при уже действующих правилах `require_write`
  и `require_admin`. Не передавать служебные токены LLM, в логах,
  URL, GitHub Issues, Tool Ledger или внутри agent workspace.
- HTTPS обязательно за исключением явно доверенного локального тестового
  подключения. Локальное окружение без API auth **не означает** production
  готовность.

## Выдача и продление

1. Доверенный worker выполняет `POST /api/v1/tasks/{task_id}/claim`
   с `{"agent_id":"..."}`. Ответ `201` по-прежнему содержит старые поля
   `AttemptResponse`, а при включённой опции дополнительно:
   `lease_token` (неповторяемый секрет), `lease_generation` (номер
   попытки) и `lease_expires_at` (UTC). `Cache-Control: no-store`.
2. Сервер хранит **только SHA-256** токена в отдельной таблице
   `attempt_leases`, связан с исходным `attempt_id/agent_id` и номером
   поколения. Нельзя создать второй действительный токен для той же
   попытки, даже если исходный ответ HTTP был потерян. В таком случае
   нужно операторское разбирательство, а не автоматический replay.
3. Worker вправе продлевать **ещё действительное** разрешение через
   `POST /api/v1/tasks/{task_id}/attempts/{attempt_id}/lease/renew`
   с `{"agent_id":"...","lease_token":"..."}`.
   Сервер проверяет токен, статус attempt/task/agent/run, соответствие
   task id, поколение и время истечения. Возвращает только новые
   `generation/expires_at` (без токена), также `no-store`.
4. Просроченная, отозванная, чужая или завершённая попытка получает
   `409 Conflict` и **не может быть возобновлена продлением**.
   Просрочка сама по себе **не помечает** задачу завершённой, не
   создаёт retry и не изменяет quarantine.
5. Авторизованный администратор может выполнить
   `POST /api/v1/tasks/{task_id}/attempts/{attempt_id}/lease/revoke`.
   Это необратимый для данного токена переход `active → revoked`;
   повторный вызов идемпотентен. **Это только отзыв полномочий, а не
   гарантированная остановка уже исполняющегося инструмента**.

## Как защищается реально выполняемая операция

В **доверенном совместно размещённом SQLite tool executor** доступен
`TrustedSqliteAttemptFence(..., lease_token=token, require_lease=True)`.
Он держит SQLite `BEGIN IMMEDIATE` через **весь** разрешённый
`read_file/write_file`, проверяет под той же блокировкой действующий
lease, agent/attempt generation, отсутствие expiry/revocation.
Серверный revoke, завершающий status transition или recovery **не может
закоммититься**, пока эта локальная операция не завершилась; следующий
tool-call после этого перехода блокируется `ATTEMPT_FENCED`.

**Важно:** истечение TTL во время уже допущенной операции не отменяет
операцию. Только для явного SQL `revoke`/status transition есть
сериализуемое отношение commit к окончанию I/O. Автоматическое
«принудительное прерывание» внешней операции здесь не реализовано.

## Атомарная приёмка результата / завершение с ошибкой

При `ORCH_ATTEMPT_LEASE_ENABLED=1` оба endpoint:
`POST /api/v1/tasks/{task_id}/attempts/{attempt_id}/submit`
и `POST .../fail` требуют **`X-Attempt-Lease: <opaque-token>`**
в заголовке вместе с обычным `X-API-Key`. Это разные секреты:
API key разрешает доступ к маршруту, а Lease привязан к конкретной
попытке и исполнителю. Передавать Lease через query string нельзя.

При положительном контракте сервер внутри **одной SQL-транзакции**
атомарно переводит соответствующий lease `active → revoked`, проверяя
хеш токена, срок, generation, attempt и владельца. В той же транзакции
фиксируются статус/выход попытки, результат проверки контракта и
изменение задачи. Конкурентные revoke и renew выполняются через
условный SQL UPDATE: победить может только одна допустимая операция.
При отсутствии заголовка, неверном/просроченном/отозванном токене
сервер возвращает `409` (без значения секрета), **не меняет**
результат задачи и не создаёт попытку повторно.

Доверенный `NativeHttpWorker(require_lease=True)` добавляет
заголовок **только** в запрос `submit`. При потере Lease он
прерывает выполнение, не отправляя ни `submit`, ни `fail`.
При отключённом Lease старый HTTP/API-контракт поддерживается.

**Граница гарантии:** этот SQL-fence защищает **финальное принятие
результата**. Он не может отменить внешний HTTP/Git/shell side effect,
который старый runner начал до отзыва разрешения. Для этого по-прежнему
требуется привилегированный tool gateway с собственной границей
исполнения, а для PostgreSQL/межхостовой среды — отдельные защищённые
транзакционные блокировки и негативные E2E. Простой renew heartbeat
ещё не означает exactly-once.

## Deployment ограничения и угрозы

- Не передавать путь RW SQLite агенту/модели. Описанный режим — только
  для доверенного privileged executor на **одном локальном хосте**,
  с приватной базой за пределами workspace; сетевые файловые системы
  и несколько хостов не поддерживаются.
- Публичный REST renew **не является допуском к side effect**. Простая
  проверка lease перед записью вне барьера всё ещё оставляет гонку
  `check → revoke → write`. Подключать нужно именно enforcement gate
  в доверенном исполнителе, а не текстовую инструкцию агенту.
- В отдельном опциональном режиме `NativeHttpWorker(require_lease=True,
  leased_runner=trusted_runner, lease_renew_interval_seconds=1.0)` получает
  одноразовый токен из ответа `claim`, передаёт его **только доверенному**
  `leased_runner(task, attempt_id, lease_context)`, периодически продлевает
  lease через сервер и проверяет его ещё раз перед `submit`. Отклонённый
  renew, транспортный сбой, некорректный generation или истечение срока
  приводят к остановке дальнейшего выполнения HTTP-worker: **без submit,
  fail или автоматического повтора**. Запущенной async-корутине отправляется
  cancellation; если она не поддерживает отмену, это НЕ гарантирует
  остановку процесса или побочных эффектов.
- **Доверенный remote tool gateway всё ещё НЕ внедрён.** Вызов
  `leased_runner` сам по себе не заставляет его использовать
  `TrustedSqliteAttemptFence` и не защищает внешний shell/HTTP/Git.
  Серверные `submit/fail` уже защищены атомарной SQL-проверкой
  действующего Lease в одной транзакции с изменением задачи. При этом
  **отзыв разрешения не останавливает ранее запущенный внешний side
  effect**, который не проходит через доверенный tool gateway.
  **Не включать `ORCH_ATTEMPT_LEASE_ENABLED=1` в рабочем удалённом
  workflow без интеграции executor и end-to-end приёмки.**
- Для PostgreSQL, другой машины, shell/Git/HTTP нужен отдельный
  authenticated privileged tool gateway, транзакционное владение/lease
  поколения и side-effect boundary на принимающей стороне.
- Ошибка после записи файла, но до `Tool Ledger SUCCEEDED` остаётся
  `CLAIMED` и требует reconciliation. Никакого auto-replay и
  недоказанных exactly-once утверждений.
- Отзыв lease не выключает ESTOP, не снимает карантин и не делает
  `CONFIRMED_NO_SIDE_EFFECT` истинным без внешнего доказательства.

## Тесты/приёмка

- `orchestration-server/tests/test_attempt_leases.py` — однократная
  выдача, секрет только в HTTP claim, хеш в БД, истечение, продление,
  revoke, неправильный владелец/task, отключённый режим.
- `tests/native_agent_e2e/test_native_contract_pipeline.py` —
  настоящий SQLite orchestration DB, успешный fenced write, отказ после
  отзыва/истечения и управляемая гонка: revoke ожидает завершения
  ранее допущенной операции.

**Checkpoint:** серверное Lease и ко-локальный SQLite barrier реализованы
отдельно. Для закрытия P0 #33/#38 необходимы доверенный удалённый шлюз,
серверный renew loop, PostgreSQL-compatible locking, cross-host E2E,
наблюдаемость и независимое ревью каждого компонента.

### Доверенный HTTP-worker: дополнительный офлайн-тест

`orchestration-server/tests/test_native_http_worker.py` проверяет
`require_lease=True` c `leased_runner`: получение токена без его
добавления в модельные task-data; многократный heartbeat renew при долгом
ожидании runner; revocation во время работы с отменой корутины и отсутствием
submit; отказ от вызова runner, если в claim отсутствует разрешение.
Старые `NativeHttpWorker(runner=...)` работают без изменений, поскольку
новый режим не включён по умолчанию.

Важно: `RemoteWorkerError` сознательно не публикует токен, тело ответа
ошибки, абсолютный URL или внешнюю трассировку. После потери lease
попытка остаётся неоднозначной и требует разбирательства, а не повторного
автозапуска.
