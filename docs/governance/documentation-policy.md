# Порядок сопровождения документации

Версия 0.2, проект #340 для согласования. Русский — основной язык продукта, инструкций, эксплуатации и организационных материалов. Английский допустим для технических спецификаций, машинных контрактов, кода, CLI, исходных evidence. Не создавать вторую редактируемую копию перевода.

## Реестр и ответственность

[Реестр документов](documentation-inventory.md) объясняет машинный реестр documentation-inventory.json. Каждая Markdown/JSON/YAML запись внутри docs имеет статус, владельца области (по OWNERSHIP, не фиктивный GitHub reviewer), язык/причину исключения и состояние review. UNKNOWN означает отсутствие подтверждения; canonical означает редактируемый источник, не принятую реализацию. Архивные evidence не переписывать. Git blob исходного historical документа фиксируется в originalBlob; CI сравнивает текущий Git tree с реестром и базовой веткой. Нельзя скрыть изменение удалением записи или сменой статуса historical. Новый архив добавляется отдельным файлом. При добавлении, удалении или переносе документа обновлять реестр в том же PR.

ADR редактировать в docs/adr; старые адреса VitePress используют include. [Индекс](../developer/architecture-decisions/adr-index.md) сверяется с источником, а не подменяет его. Исторические ссылки внутри ADR сохраняются как свидетельство исходного контекста; не интерпретировать их как актуальные команды.

## Doc impact

При изменении API, конфигурации, поведения, ролей, security boundary или миграции обновить соответствующий канонический документ в том же PR. При отсутствии влияния заполнить отдельную строку `Doc impact: none — <причина>` в PR. Автоматический guard перезапускается и при редактировании описания PR, проверяет наличие изменения docs или явного обоснования для затронутых областей, но не качество обоснования — это обязанность reviewer. Не выдавать техническое исключение за освобождение от актуальности документации.

## Проверки

Существующий docs CI сохраняет npm ci, VitePress build, link resolver, generated links, audit и Chromium smoke. Дополнительный offline guard проверяет полное покрытие реестра, допустимые статусы, owner, причины исключений, безопасные пути и единственный источник ADR; unit tests проверяют отказы. CI дополнительно сверяет `checked-examples.json`: существование tracked paths, наличие make targets, соответствие HTTP method/path сохранённому OpenAPI. JSON Schema 2020-12 обоих реестров компилируется существующим locked Ajv; положительные и отрицательные fixtures проверяются в CI. Это ограниченный проверяемый набор, не исполнение произвольных команд или подтверждение всей документации. Docs CI запускается на каждом PR и push в main без фильтров путей: реестр может ссылаться на любой tracked файл (например, VERSION, AGENT_GITFLOW_RULES.md или scripts/check_pilot_readiness.py), а его удаление или переименование должно приводить к проверке. Это увеличивает число запусков Docs CI; отмена устаревших PR-проверок сохраняется. Остальные примеры требуют содержательной проверки. Не считать guard доказательством перевода, schema compatibility или E2E.

## Границы технических спецификаций

[Карта технических документов](technical-document-boundaries.md) различает продуктовые ADR, проектные P8.3 и архивный аудит, фиксирует различия schema blobs без изменения контрактов. При ревью проверять не только язык, но и фактический источник истины. Исторические, superseded и удалённые документы не удовлетворяют doc impact автоматически.

## Остаточные условия приёмки

Перевод трёх оставшихся активных security/QA runbooks выполнен. [Указатель требований и контрактов](requirements-and-contracts.md) теперь ведёт к PRD, реестру контрактов и RTM, технически интегрированным в main; они остаются проектами до согласования. Требуется подтверждение классификации остальных материалов и содержательная проверка русскоязычных документов владельцами, проверка legacy-примеров и внешних references, фактический CI на точном SHA и независимое review. Production deployment и live provider не подтверждены. Оригиналы прошлых редакций доступны в Git.

### Защита исторических данных на main

При PR и push в защищённый main проверка сравнивает Git tree с фактической базой (для push — `github.event.before`). Изменение исторического файла вместе с originalBlob или удаление/переклассификация исторической записи отклоняется. Первое объединение ADR-дубликатов подтверждает одинаковые исходные blob; дальнейшие PR сохраняют mapping и исходный blob, даже когда канонический ADR обновляется. Изменение/удаление совместимого ADR-адреса требует отдельного согласованного решения по миграции. При PR diff учитывает обе стороны rename (`--no-renames`), поэтому перенос или удаление исходника из области API/config не обходит doc impact. На push нет PR body: проверяется историческая сохранность и структура, не повторяется PR-специфичное обоснование. Ручной запуск без base проверяет только текущий tree; не считать его доказательством сохранности относительно предыдущего main.

## Навигация и проверка портала

PRD, контракты и трассируемость доступны из одного раздела навигации; машинные реестры остаются исходниками в Git. Chromium проверяет фактические переходы, заголовки и ссылки на русскоязычные разделы. Якоря русских заголовков не должны терять буквы при формировании slug. Это дополняет проверку generated links, которая проверяет существование страниц и assets, но не все фрагменты URL. Исторические адреса ADR сохраняются.
