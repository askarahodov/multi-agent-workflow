# Владение компонентами и GitHub review

Задача #345. Проект для согласования. Каноническая карта областей — [OWNERSHIP](../architecture/OWNERSHIP.md). CODEOWNERS должен отражать утверждённых людей/команды с доступом и реальной независимой проверкой, а не создавать фиктивные идентичности.

Проверенный факт: репозиторий принадлежит askarahodov. Отдельные GitHub identity владельцев подсистем и независимых проверяющих в текущей сессии не согласованы. Не назначать автоматически владельца репозитория единственным reviewer всех подсистем: это не доказывает разделение полномочий.

Перед добавлением CODEOWNERS: утвердить владельцев для orchestration, agent-management, QA, runtime, frontend, shared, tools, docs, CI; проверить их GitHub доступ, покрытие путей и отсутствие ошибочных паттернов. Отдельно проверить ruleset #44 и обязательное review. CODEOWNERS не заменяет branch protection.

В этом PR GitHub поддерживаемые файлы CONTRIBUTING/SECURITY и шаблоны размещены в .github, чтобы не конфликтовать с корневым layout guard. Осталось согласование CODEOWNERS, проверка шаблонов на реальном GitHub и enforcement применимых полей.

## Ветки и завершение задач

GF-06/GF-07/GF-10 обязательны: один Issue/PR/ветка, после принятого merge удалить source branch и связанный чистый локальный worktree; проверить удаление на GitHub и локальном хосте. Не удалять ветку только потому, что закрыт PR, исчез upstream или истекло 48 часов. Учитывать squash receipt, точный head, опубликованный merge, зависимые PR и уникальные коммиты. Ветки без PR, release/hotfix и отдельная external QA coordination line подлежат явной классификации. Автоматический удалённый audit и безопасная локальная очистка в scripts/git/maintenance; см. docs/branch-cleanup. GitHub auto-delete проверяется по API, не предполагается.

## Ограничение незавершённой работы (WIP)

Решение владельца от 26.11.2026: максимум 5 одновременно незавершённых задач с рабочими ветками/PR, предпочтительно 3. Считать draft, ожидающие CI/review и активные рабочие ветки без PR; stacked PR не исключать из лимита. Служебные и поддерживаемые релизные ветки инвентаризируются отдельно. При превышении лимита запрещено начинать новые задачи или создавать новые рабочие ветки/PR: сначала завершить текущие либо обоснованно разрешить их блокеры. Не закрывать Issues/PR искусственно ради лимита. Считать один исходный Issue, одну ветку и один PR основной единицей работы. Контроль выполняют координатор, автоматизация разработки и принимающий; это не автоматический GitHub ruleset.

Приоритет стабилизации: #359 и #357; затем #316/#317 и #350–#356 с соблюдением зависимостей. #354 зависит от #352: проверки для PR в main не запускаются полностью на stacked base. Не ослаблять CI; после принятого merge родителя перепроверить кандидат #354, перенести base на main и получить все обязательные проверки. Не создавать дублирующий PR. До получения независимого согласования и выполнения GF-09 merge запрещён.
