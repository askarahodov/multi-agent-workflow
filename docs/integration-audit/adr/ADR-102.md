# ADR-102: Ownership of State

**Status:** Accepted
**Date:** 2026-10-12
**Deciders:** sdlc-architect (TASK-01 EPIC-INT E2)
**Related:** 03-ownership.md, 01-architecture-audit.md (Risk R4), ADR-101, ADR-103

---

## Context

The codebase contains **duplicate ownership of agent state** across two subsystems:

| Subsystem | Entity | Table | Status Values | Purpose |
|-----------|--------|-------|---------------|---------|
| Orchestration Server | `Agent` | `agents` | `inactive`, `idle`, `busy`, `terminated` | Runtime scheduling: which agent is available to claim tasks |
| Agent Management | `AgentInstance` | `agent_instances` | `pending`, `running`, `completed`, `failed`, `terminated` | Configuration + execution lifecycle: model, tool policy, system prompt |

**Problems caused:**
1. **No single source of truth** — an agent's "status" is ambiguous (scheduling vs execution)
2. **Drift risk** — Orchestration marks `Agent.busy` when task claimed; Agent Management marks `AgentInstance.running` when started. No synchronization mechanism exists.
3. **Confusion for consumers** — Frontend, agents, and operators don't know which status to trust.
4. **Runtime Hardening adds third state** — `AgentState` enum (`created`, `running`, `paused`, `degraded`, `failed`, `terminated`) in container runtime, completely disconnected.

---

## Decision

**Explicit ownership boundaries per domain:**

| Domain | Owner | Entities | API |
|--------|-------|----------|-----|
| **Project / Workspace / Environment / Team** | Orchestration Server | `projects`, `workspaces`, `environments`, `teams` | `/projects`, `/workspaces` |
| **Contract (JSON Schema)** | Orchestration Server | `contracts` | `/contracts` |
| **Workflow Definition (design-time)** | Orchestration Server | `workflow_definitions`, `workflow_versions` | `/api/v1/workflows/definitions*` |
| **Workflow Run / Task / Attempt (runtime)** | Orchestration Server | `workflow_runs`, `tasks`, `task_attempts`, `saga_events` | `/workflows/runs`, `/tasks/*` |
| **Agent Scheduling Status** | **Orchestration Server** | `agents` (`idle`/`busy`/`terminated`) | `/agents/register`, `/agents` |
| **Agent Definition (template)** | Agent Management | `agent_definitions` | `/api/v1/agents/definitions` |
| **Agent Instance (config + execution lifecycle)** | Agent Management | `agent_instances` (`pending`/`running`/`completed`/`failed`/`terminated`) | `/api/v1/agents/instances` |
| **Provider / Model Profile / Tool Policy** | Agent Management | `providers`, `model_profiles`, `tool_policies` | `/api/v1/providers`, `/api/v1/model-profiles`, `/api/v1/tool-policies` |
| **Token Usage / Accounting** | Agent Management | `token_usage` | `/api/v1/usage/*` |
| **Container / Isolation / Resources** | Runtime Hardening | (cgroups v2, FS overlay, container lifecycle) | `/agents`, `/workspaces` (Runtime API) |

### Synchronization Protocol

1. **Agent registration:** When Agent Management creates an `AgentInstance`, it **also registers** a corresponding `Agent` in Orchestration Server (same ID) with status `idle`. Orchestration owns the `idle`/`busy` scheduling state.
2. **Task claim (Orchestration):** `claim_task` → sets `Agent.busy` → calls Runtime `create_agent` with `AgentSpec` built from Agent Management data (definition + model profile + tool policy).
3. **Task execution (Runtime):** Container runs; Runtime reports `AgentState` (`running`/`paused`/`degraded`/`failed`/`terminated`).
4. **Task completion (Orchestration):** `submit`/`fail_attempt`/`block_task` → sets `Agent.idle` → calls Runtime `stop_agent`/`pause_agent`.
5. **Agent Instance lifecycle (Agent Management):** Mirrors execution: `pending` → `running` (on claim) → `completed`/`failed`/`terminated` (on task end). Updated via events from Orchestration (SagaEvent) or direct callback.

### Reference Integrity

- Orchestration `Task.assigned_agent_id` → FK to `agents.id` (Orchestration)
- Orchestration `Task.agent_definition_id` (NEW) → FK to `agent_definitions.id` (Agent Management)
- Agent Management `AgentInstance.agent_definition_id` → FK to `agent_definitions.id`
- Runtime `Agent.id` = Orchestration `Agent.id` = Agent Management `AgentInstance.id` (shared UUID)

---

## Consequences

**Positive:**
- Clear "who owns what" eliminates drift
- Orchestration remains single authority for task scheduling and workflow execution
- Agent Management focuses on configuration (definitions, models, policies) — its core domain
- Runtime Hardening stays infrastructure-only (isolation, resources), no domain state

**Negative:**
- Requires synchronization logic (events/callbacks) between Orchestration and Agent Management
- New FK `Task.agent_definition_id` in Orchestration (cross-DB reference — logical only, no FK constraint across DBs)
- Agent registration becomes two-step (Agent Mgmt creates Instance → Orchestration registers Agent)

**Migration:**
1. Add `agent_definition_id` to Orchestration `Task` model
2. Implement Agent Management → Orchestration registration callback
3. Add SagaEvent types for `agent.instance.created`, `agent.instance.completed`
4. Deprecate direct `AgentInstance` status reads for scheduling decisions

---

## Rejected Alternatives

| Option | Rejection Reason |
|--------|------------------|
| Merge Agent tables into one service | Violates platform principles: Orchestration = platform-owned scheduling; Agent Mgmt = provider independence |
| Single `Agent` entity with all statuses | Conflates scheduling availability (`idle`/`busy`) with execution lifecycle (`running`/`completed`/`failed`) |
| Event sourcing for all state | Over-engineered for v1; current state tables + SagaEvent sufficient |
| Runtime Hardening owns agent state | Runtime is infrastructure; shouldn't own domain concepts |

---

## Verification

- `03-ownership.md` table matches implementation (code review)
- No `Agent` status read in Agent Management for scheduling decisions
- No `AgentInstance` status read in Orchestration for task assignment
- Integration test: create AgentInstance → verify Orchestration `Agent` exists with `idle` → claim task → verify both transition correctly
