# ADR-103: Tool Policy Enforcement at Execution Boundary (Deny-by-Default)

**Status:** Accepted
**Date:** 2026-10-12
**Deciders:** sdlc-architect (TASK-01 EPIC-INT E2)
**Related:** 01-architecture-audit.md (Risk R3), 03-ownership.md, ADR-102, `agent-management/agent_management/tool_policy.py`, `agent-management/agent_management/services.py`, `runtime-hardening/runtime/*`

---

## Context

The codebase declares a **deny-by-default tool policy** in `agent-management/agent_management/tool_policy.py`:

- `ToolPolicyEngine.allow()` returns `False` for unknown actions and empty allow-lists (lines 61-77)
- `ToolPolicyEngine.enforce()` raises `ToolPolicyDenied` (lines 80-85)

**However, enforcement is completely disconnected from execution:**

1. **`DEFAULT_PERMISSIVE_POLICY`** exists as dead code (lines 106-112) — grants `**` / `*` for all actions; never imported anywhere (`grep` confirms only definition)
2. **`ToolPolicyEngine` instantiated in `AgentManagementService`** (`services.py:241`) but **`enforce`/`allow` never called** in `run_completion` (lines 592-665) or any other execution path
3. **No enforcement in Runtime Hardening** — container runtime, workspace manager, and resource manager don't reference tool policies
4. **No enforcement in Orchestration Server** — task execution doesn't check policies

**Effective state:** Tool policies are **declarative only** — stored, versioned, associated with agents — but **never enforced** at the point where tools are actually invoked.

---

## Decision

**Enforce tool policies at the execution boundary — deny-by-default.**

### Enforcement Points (both required)

#### 1. Agent Management: `run_completion` (LLM tool calls)
Before any LLM provider call that may invoke tools, `AgentManagementService.run_completion` MUST:
- Resolve the `AgentInstance.tool_policy_id` → `ToolPolicy.permissions`
- For each tool call in the LLM request/response cycle, call `ToolPolicyEngine.enforce(permissions, action, resource)`
- On denial: return structured error to caller (do not proceed to provider)

#### 2. Runtime Hardening: Container / Workspace / Network (OS-level enforcement)
Runtime Hardening MUST translate `ToolPolicy.permissions` into **infrastructure controls**:
- **Filesystem:** `fs_read`/`fs_write` patterns → OverlayFS mount options, bind-mount scoping, seccomp profile (via `container_runtime.py` + `SeccompProfileGenerator`)
- **Git:** `git` allow-list → Pre-commit hook / wrapper that validates subcommand
- **Shell:** `shell` allow-list → Restricted shell / command allow-list in container entrypoint
- **Network:** `network` allow-list → `nftables`/`iptables` egress rules per container cgroup (via `ResourceManager` or CNI plugin)

### Policy Resolution Order

```
AgentInstance.tool_policy_id
    → ToolPolicy.permissions (JSON)
    → If null/empty: DENY ALL (no DEFAULT_PERMISSIVE_POLICY)
    → Pass to BOTH enforcement points
```

### `DEFAULT_PERMISSIVE_POLICY` Handling

- **REMOVE** from `tool_policy.py` (dead code, security risk if accidentally used)
- Replace with **explicit test-only policy** in test fixtures: `TestToolPolicyFactory.permissive()`
- Document: "Production policies must explicitly allow required actions. No implicit defaults."

### Error Handling

- **Agent Management enforcement failure** → `ToolPolicyDenied` (RFC 9457 Problem Detail, status 403) → Task `blocked` with reason "tool_policy_denied"
- **Runtime enforcement failure** → Container/seccomp/network error → Task `failed` with reason "runtime_policy_violation" → SagaEvent recorded
- **Both enforcement layers must agree** — defense in depth

---

## Consequences

**Positive:**
- Actual security boundary: agents cannot exceed declared permissions
- Deny-by-default is now real, not aspirational
- Two-layer enforcement (application + infrastructure) catches bypasses
- Policy becomes testable: unit tests for `ToolPolicyEngine`, integration tests for Runtime

**Negative:**
- Existing agents with no/empty tool policy will be **completely blocked** (cannot read/write/execute anything)
- Requires creating default policies for existing agent definitions (migration)
- Runtime network/filesystem enforcement adds complexity (nftables, seccomp, overlayFS)
- LLM tool call interception in `run_completion` requires parsing provider-specific tool call formats

**Migration Path:**
1. Create default policies for all existing `AgentDefinition`/`AgentInstance` (e.g., `workspace-read`, `workspace-write`, `network-none`)
2. Implement Agent Management enforcement in `run_completion` (Phase 1)
3. Implement Runtime filesystem enforcement via overlayFS mount scoping (Phase 2)
4. Implement Runtime network enforcement via nftables (Phase 3)
5. Remove `DEFAULT_PERMISSIVE_POLICY` constant

---

## Rejected Alternatives

| Option | Rejection Reason |
|--------|------------------|
| Keep `DEFAULT_PERMISSIVE_POLICY` as fallback | Defeats deny-by-default; security regression |
| Enforce only in Agent Management | LLM provider may not expose all tool calls; infrastructure bypass possible (direct FS/network) |
| Enforce only in Runtime | Cannot inspect LLM tool calls (semantic actions); only sees syscalls |
| Advisory policy (log only, no block) | Doesn't satisfy "deny-by-default" requirement; audit-only is separate concern |
| Custom eBPF/LSM for enforcement | Over-engineered; seccomp + nftables + overlayFS sufficient for v1 |

---

## Verification

- **Unit:** `ToolPolicyEngine.allow/enforce` covers all 5 action kinds, glob patterns, edge cases (empty, unknown, `*`)
- **Integration (Agent Mgmt):** `run_completion` with mocked provider → tool call denied → 403 returned, task blocked
- **Integration (Runtime):** Container started with policy → `fs_write` outside allowed path → `EPERM` / seccomp kill
- **Integration (Network):** Container with `network: ["https://api.example.com/**"]` → egress to other host → dropped by nftables
- **Regression:** `DEFAULT_PERMISSIVE_POLICY` not referenced in non-test code (`grep -r` clean)
