# PRD: Multi-Agent Workflow — корпоративная фабрика разработки

Версия 0.1, проект для согласования владельцем продукта. Baseline изучения: `6e47938df1f94e783f266c8210de5c92e8c20058`. Источники: [#321](https://github.com/askarahodov/multi-agent-workflow/issues/321), [#334](https://github.com/askarahodov/multi-agent-workflow/issues/334), [исторический gap audit](../audit/PRD-TO-CODE-GAP.md), README и существующие ADR. Исходная Kanban-карта PRD Draft 1.0 не была доступна в текущей GitHub-сессии; ниже не объявляется её полным восстановлением.

## Видение

Платформа обеспечивает управляемую агентную разработку нескольких продуктовых команд: от требования до проверяемого изменения в Git, независимого QA и согласованного релиза. Люди владеют бизнес-целями, рисками и полномочиями; ИИ работает в рамках детерминированных процессов.

## Пользователи и задачи

| Роль | Сценарий |
|---|---|
| Владелец продукта | Создать/уточнить требование, выбрать проект и критерии приёмки |
| Руководитель команды | Управлять очередью, зависимостями, бюджетом и блокерами |
| Инженер | Запустить опубликованный workflow, изучить diff/PR и evidence |
| Платформенный администратор | Настроить интеграции, модели, права и политики |
| Независимый QA/security/auditor | Проверить candidate и evidence без полномочий автора |
| Оператор | Согласовать разрешённое действие, восстановить неоднозначную попытку |

## Границы

В scope: организация/команды/проекты, native agent runtime, версионированные workflow и profiles, контракты, безопасный tool execution, Git/CI connectors, QA, портал, наблюдаемость, on-prem и air-gap.
Вне scope: имитация компании AI CEO как обязательная модель, замена Jira/Bitbucket/CI, автоматический production deploy без отдельного разрешения, обязательный Hermes/сторонний CLI или внешний LLM, создание собственного foundation model.

## Основные сценарии

1. Организация создаёт команды и проекты, настраивает scopes и отдельные credentials. Чужие проекты недоступны.
2. Из Jira поступает задача; проверенный webhook создаёт один run на опубликованном workflow. Planner предлагает ограниченный DAG; Control Plane валидирует.
3. Native workers исполняют разрешённые действия в изолированных attempts; изменения фиксируются в Git. QA проверяет candidate SHA, CI и evidence; человек принимает применимое решение.
4. При сбое неоднозначная операция quarantined; оператор сверяет evidence, а не повторяет side effect вслепую.
5. Оператор видит фактический статус, затраты, блокеры и историю; для закрытого контура не требуется внешняя сеть.

## Требования и критерии

Канонический структурированный перечень — `docs/product/requirements.json` (машиночитаемый файл в репозитории; не страница VitePress). Каждое требование имеет уникальный ID, приоритет, владельца, критерий и способ проверки. Статус draft означает не согласовано, а не реализовано. #338 добавляет матрицу реализации и evidence, не копирует текст требований.

Нефункциональные параметры (SLO availability, p95 queue/dispatch latency, concurrency, RPO/RTO, retention, budget ceilings, accessibility target и поддерживаемые версии) должны быть согласованы владельцами продукта/операций/security до production acceptance. Числа не придуманы.

## Уровни готовности

LOCAL_BOOTABLE: установка и health; UI_MANUAL_TESTABLE: операторский путь; SDLC_MVP_ACCEPTED: реальные evidence и независимый QA; ENTERPRISE_ACCEPTED: две команды, tenant isolation, политики, согласованные SLO, recovery, approved live run и эксплуатационный стенд. Не выводить один уровень из другого.

## Термины

- Control Plane — доверенное управление состоянием, правами и процессами.
- Worker — экземпляр выполнения попытки; профиль — версионированное описание роли.
- Run/Task/Attempt — запуск, задача и конкретная попытка; не взаимозаменяемы.
- Evidence — проверяемый артефакт с provenance и scope, не отчёт модели.
- Quality Gate — независимая проверка; approval — отдельное решение уполномоченного человека.
- Blueprint — опубликованный шаблон workflow с версиями и контрактами.
