# Трассируемость требований

Версия 0.1, проект для согласования. Задача #338; зависит от #336 (PR #352) и #337. Источник требований: `docs/product/requirements.json`. Матрица: `docs/product/traceability.json`. Машинные файлы хранятся в Git, а не как страницы VitePress.

Первичный реестр содержит 20 требований, все имеют статус planned: независимое соответствие реализации не подтверждено. Issue — связь с планом, а не evidence. Статусы: planned, implemented (PR и SHA), verified (результат теста/CI на том же SHA), accepted (согласованное требование, independent approval, нет блокеров), blocked (причина). 

Проверка `node scripts/check-requirements.js` валидирует уникальность, обязательные поля, покрытие, привязку Issue, полноту и согласованность evidence с указанным candidate SHA. `node --test scripts/check-requirements.test.js` проверяет отрицательные сценарии. CI использует существующий Docs check. Формат evidence не подтверждает подлинность URL, идентичность reviewer или актуальность удалённого SHA: эти факты проверяются независимо через GitHub/QA и operator review, до #349/#333. Не считать структурную проверку принятием. Матрица содержит ссылки на существующие ADR/архитектурные документы и исходные контракты; ссылки обозначают область проверки, а не утверждение, что исторический ADR принят или контракт достаточен. Пустой список означает TBD, не N/A. Поле release связывает принятый candidate с релизом только при одинаковом SHA; squash/позднейшие release commits требуют отдельного доказательства соответствия (до этого release=null). Проверка внешних evidence и согласование контрактных IDs остаются обязательными перед окончательной приёмкой.

Не копировать текст PRD в матрицу; менять требование в каноническом реестре. При изменении candidate пересмотреть все связанные evidence, не переносить автоматически PASS с предыдущего SHA.

## Отчёт о пробелах

Команда `node scripts/check-requirements.js` генерирует отчёт непосредственно из канонических JSON-файлов: приоритет, требование, Issue, статус, ссылки на архитектуру/контракты, релиз и блокеры. Она также проверяет существование локальных файлов, отклоняет выход за границы репозитория, повторные ссылки, формальное саморевью и несовпадение SHA релиза. Это structural check, не внешняя проверка подлинности. История GitHub и реальные CI/review receipts проверяются принимающим независимо; фиктивная строка в JSON не является approval.
