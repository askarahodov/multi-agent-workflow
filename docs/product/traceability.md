# Трассируемость требований

Версия 0.1, проект для согласования. Задача #338; зависит от #336 (PR #352) и #337. Источник требований: `docs/product/requirements.json`. Матрица: `docs/product/traceability.json`. Машинные файлы хранятся в Git, а не как страницы VitePress.

Первичный реестр содержит 25 требований, все имеют статус planned: независимое соответствие реализации не подтверждено. Issue — связь с планом, а не evidence. Статусы: planned, implemented (PR и SHA), verified (результат теста/CI на том же SHA), accepted (согласованное требование, independent approval, нет блокеров), blocked (причина). 

Проверка `node scripts/check-requirements.js` валидирует уникальность, обязательные поля, покрытие, привязку Issue, полноту и согласованность evidence с указанным candidate SHA. `node --test scripts/check-requirements.test.js` проверяет отрицательные сценарии. Валидатор использует единый `scripts/validate-requirements.mjs` из #336, а CI запускает RTM на каждом PR/push через Quality Gate. Формат evidence не подтверждает подлинность URL, идентичность reviewer или актуальность удалённого SHA: эти факты проверяются независимо через GitHub/QA и operator review, до #349/#333. Не считать структурную проверку принятием. Матрица содержит ссылки на существующие ADR/архитектурные документы и исходные контракты; ссылки обозначают область проверки, а не утверждение, что исторический ADR принят или контракт достаточен. Пустой список означает TBD, не N/A. До согласования отдельного формата подтверждённого N/A статус accepted и release linkage требуют непустых architecture_refs и contract_refs; planned/implemented/verified могут сохранять TBD, но это не финальная приёмка. Для FR-ORCH-004 и FR-INT-001 (и любых требований с именованными acceptance_cases) verified/accepted требуют по каждому case отдельного структурного CI evidence с case_id, test_id, verdict=pass и candidate SHA. Один общий CI PASS не заменяет отрицательные сценарии. Проверяющий дополнительно подтверждает подлинность результата и соответствие теста сценарию. Поле release связывает принятый candidate с релизом только при одинаковом SHA; squash/позднейшие release commits требуют отдельного доказательства соответствия (до этого release=null). Проверка внешних evidence и согласование контрактных IDs остаются обязательными перед окончательной приёмкой.

Не копировать текст PRD в матрицу; менять требование в каноническом реестре. При изменении candidate пересмотреть все связанные evidence, не переносить автоматически PASS с предыдущего SHA.

## Отчёт о пробелах

Команда `node scripts/check-requirements.js` генерирует отчёт непосредственно из канонических JSON-файлов: приоритет, требование, Issue, статус, ссылки на архитектуру/контракты, релиз и блокеры. Она также проверяет существование локальных файлов, отклоняет выход за границы репозитория, повторные ссылки, формальное саморевью и несовпадение SHA релиза. Это structural check, не внешняя проверка подлинности. История GitHub и реальные CI/review receipts проверяются принимающим независимо; фиктивная строка в JSON не является approval.


## Согласованность текущих доказательств

Матрица хранит снимок актуального candidate SHA, а не журнал повторных запусков. Для `verified` и `accepted` все включённые CI receipts должны иметь `verdict=pass`; для `accepted` все включённые approval receipts также должны иметь `verdict=pass`. Положительный результат не скрывает отрицательный, отменённый, неопределённый или ожидающий результат на том же SHA. Устаревшие/заменённые результаты сохраняются в истории GitHub/QA; проверяющий отдельно подтверждает действительное замещение, актуальность и полномочия до изменения снимка. Это структурный fail-closed контроль, не внешняя проверка подлинности и не автоматическое разрешение merge. Отсутствие independent approval нельзя исправить фиктивной строкой evidence.

## Привязка сценариев и проверяемый отчёт

Одна пара reference + test_id в пределах требования не может одновременно подтверждать разные acceptance cases. Для параметризованных тестов использовать полный идентификатор с параметром; отдельные CI runs допускаются. Неизвестные case_id и привязка case_id к записи не типа ci отклоняются. Для accepted каждая approval-запись должна иметь указанного reviewer, отличного от implementer; независимая запись не скрывает самоприёмку. Это проверка согласованности полей, не аутентификация личности.

Генерируемый отчёт дополнительно показывает PR, candidate SHA, заявленные evidence (reference, test_id, case_id, verdict, reviewer, commit_sha) и идентификаторы сценариев, для которых нет PASS в матрице. Пустой список пробелов в сценариях не означает внешнее подтверждение. Не использовать этот вывод вместо получения настоящих результатов CI и review через доверенный канал.


## Внешняя проверка GitHub receipts

`node scripts/verify-requirement-evidence.mjs` — отдельная read-only операторская проверка с доверенного checkout, **не запускать код непроверенного PR с привилегированным токеном**. Опциональный `GITHUB_TOKEN` передавать только из защищённой среды с минимальными правами чтения. При недоступности API/permissions — BLOCKED, не PASS. URL evidence не используется как сетевой адрес: API origin и repository закреплены в verifier, только GET, без redirects, с ограниченной пагинацией и timeout. Никаких write API, выдачи APPROVED, изменения матрицы или авто-merge.

Для CI metadata поддерживается канонический URL `https://github.com/askarahodov/multi-agent-workflow/actions/runs/<run-id>/job/<job-id>` и `test_id: job:<job-id>/step:<step-number>`. Проверяются текущий exact PR head, repository, PR association, successful run, latest attempt, successful job и step; повторное чтение run и PR отсекает наблюдаемую гонку. Доказательство конкретного теста вида pytest nodeid, Playwright test title или покрытия case семантикой не выводится из зелёного step: требуется отдельный доверенный test artifact/независимый анализ. Статус JOB_STEP_CONFIRMED не равен verified или accepted.

Approval receipt — URL `.../pull/<pr>#pullrequestreview-<id>`: exact current SHA, настоящий APPROVED от User (не Bot), не author/implementer, актуальная review history без CHANGES_REQUESTED/pending, collaborator permission write/maintain/admin. Это не доказательство полного separation of duties, отсутствия unresolved threads, всех required gates, product acceptance или безопасности; применяется GF-09 и независимый reviewer. Release linkage, индивидуальные test artifacts, и внешние CI providers остаются отдельными проверками. Результат RECEIPTS_INSPECTED_NOT_ACCEPTED не повышает состояние. Planned/blocked не вызывают API. Действующий offline CI проверяет mock REST fixtures и structural validation; реальная проверка выполняется оператором из доверенной среды. Все 25 canonical requirements сохраняются planned.


### Доказательства отдельных pytest-тестов

Quality Gate сохраняет минимальные JSON-отчёты всех шести backend suites и root suite после успешного pytest, с точными classname::name (включая параметры), passed/skipped, run/attempt/head/base/checkout. Не сохраняются stdout, traceback и исходный XML. Имена required jobs не изменены; отсутствие отчёта или upload failure блокирует соответствующий job. Retention 30 дней.

Для проверки отдельного теста задайте `kind: ci`, канонический run/job URL, `artifact_id` (числовой ID GitHub Actions), `test_id: pytest:<classname>::<name>`, verdict pass и точный SHA. Операторский verifier проверяет base SHA из PR association, latest run attempt, успешные шаги pytest/producer/upload, единственный артефакт ожидаемой suite/attempt, размер, GitHub SHA-256 digest, provenance и точное passed имя. ZIP загружается read-only через `gh api --hostname github.com`, проверяется Python 3 без извлечения на диск; размер ограничен, лишние members и дубли JSON ключей отклоняются. Требуется доверенный checkout, gh с read-only Actions доступом и Python 3. Просроченный/отсутствующий артефакт — BLOCKED, не PASS. Результат PYTEST_RESULT_CONFIRMED подтверждает записанный тестовый результат, не семантику сценария, неизменность workflow или независимость reviewer; проверять доверие к CI definition отдельно. Для Vitest, Playwright, внешних CI и release пока остаётся отдельная приёмка. При изменении PR base старый CI receipt не принимается; исторические merged candidates с изменившимся base требуют отдельной архивной проверки. Все canonical records по-прежнему planned.

Диагностика CI: в первоначальном тестовом fixture имя `run` одновременно обозначало объект REST workflow run и функцию запуска проверки. Отрицательная мутация `run.path` изменяла функцию, а не реальные входные данные; исправлено разделением `run`/`inspect`, добавлены именованные сценарии и проверки конкретной причины отказа. Production guard не ослаблен.


### Доказательства отдельных frontend-тестов

В том же Quality Gate добавлены четыре отдельных набора evidence: vitest (unit), browser-mock (React + mocked network), compose-browser (реальные локальные API) и compose-ticket (отдельный ticket-only browser). Существующие команды, retry policy, обязательные job names и conditional Compose scope сохранены; при выполнении тестового шага отсутствие отчёта или upload failure блокирует job. JSON репортёры Vitest/Playwright передают в минимальный артефакт только относительное имя тестового файла, идентификатор, результат и provenance; исходные JSON, stack traces, attachments не публикуются. Playwright flaky, expected failure, skipped не являются PASS. Vitest pending/todo/skipped и явно отражённые retry также не являются PASS.

Идентификатор evidence: `frontend:<suite>:<relative-file>::<identity>`, для Vitest identity = fullName, для Playwright = JSON-массив пути названий suites/spec/project. Полный список берётся из maw-frontend.json в конкретном артефакте `rtm-frontend-<suite>-<attempt>`. Обязательны run/job URL и artifact_id. Проверяются соответствующие suite/job/test step/producer/upload, digest, head/base/run/attempt и индивидуальный passed. Отдельные suite не взаимозаменяемы: mocked network не доказательство реального API. FRONTEND_RESULT_CONFIRMED не является semantic acceptance. Реальные Jira/Bitbucket/Jenkins/TeamCity evidence adapters относятся к #326; отсутствие внешней доверенной интеграции остаётся BLOCKED, generic job PASS не подменяет внешний test receipt. Для release mapping и независимой приёмки сохраняются ранее описанные ограничения.
