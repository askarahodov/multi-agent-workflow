## 1. Container / Sandbox Isolation Best Practices

### 1.1 The isolation spectrum

Isolation primitives form a graduated spectrum, trading **security boundary strength** against
**performance, density, and operational complexity**:

| Tier | Mechanism | Boundary | Typical startup | Memory overhead | KVM required |
|---|---|---|---|---|---|
| 0 | Plain `runc`/`crun` container | Shared host kernel, namespaces + cgroups + seccomp | ~50 ms | ~0 | No |
| 1 | Process sandbox (`bubblewrap`, `nsjail`, Landlock) | User/mount/PID/net ns + seccomp | 2–5 ms | ~0 | No |
| 2 | Userspace kernel (`gVisor`/`runsc`) | Sentry intercepts syscalls in Go | ~20–50 ms | 20–50 MB | **No** (systrap) |
| 3 | MicroVM (`Kata + Firecracker/Cloud-Hypervisor/QEMU`) | Hardware virtualization (KVM) | 100–200 ms | 20–180 MB | **Yes** |
| 4 | Full VM | Hypervisor | seconds | GBs | Yes |

Key finding: **`runc`/standard containers share the host kernel**, so a kernel-level escape (a
namespace-handling bug or a kernel CVE) defeats them entirely. All process sandboxes (bubblewrap,
nsjail, firejail) share this same limitation — "none of them is a VM… a kernel-level container-escape
vulnerability defeats all three equally." (bigiron.cc, wuu73.org field guide). For a genuinely
**adversarial** threat model you need a VM; for defense-in-depth you should layer a process sandbox
*inside* a container or VM so it becomes a second barrier, not the only one.

### 1.2 gVisor

- Implements a **userspace kernel ("Sentry") in Go** that intercepts container syscalls before they
  reach the host kernel, reimplementing Linux syscall semantics in a memory-safe language
  (safeguard.sh; MIT study). The host kernel surface exposed to the workload is drastically reduced.
- **Compatibility gap:** gVisor implements roughly 240 of ~400 Linux syscalls; io_uring, eBPF, some
  ioctls are unsupported or partial. This is the principal operational risk for arbitrary agent
  toolchains.
- **Performance:** I/O-heavy and memory-management-heavy workloads see significant overhead
  (10–30% on I/O-heavy paths); CPU-bound workloads are near-native. Peer-reviewed work (MIT
  *"Blending Containers and VMs"*, Cluster Computing 2022) found gVisor slower for memory management
  and network streaming but strictly stronger syscall restriction than plain containers.
- **No KVM needed** (systrap/ptrace platforms) — deployable on nested-virtualization environments and
  CI runners where `/dev/kvm` is absent. This is a decisive operational advantage.
- Kubernetes integration via `RuntimeClass` with handler `runsc`; GKE offers it first-class as "GKE
  Sandbox."

### 1.3 Kata Containers

- Runs **each pod inside a lightweight VM** with its own guest kernel, backed by Firecracker, Cloud
  Hypervisor, or QEMU. The isolation boundary is the **hypervisor (KVM)**, not namespaces
  (safeguard.sh; edera.dev).
- **Performance:** boot 100–200 ms; memory overhead ~20–50 MB per VM (Kata's own figures; some sources
  cite up to 180 MB depending on VMM/agent); I/O overhead ~5–15% for storage and networking; CPU
  near-native. Significantly faster than gVisor for I/O-intensive workloads because a real kernel runs,
  just an isolated one.
- Requires **KVM / virtualization extensions** — unavailable in some nested-VM / restrictive cloud
  environments.
- Kubernetes integration via `RuntimeClass` handler `kata-qemu` / `kata-fc`.

### 1.4 Firecracker microVMs

- A **minimal VMM** exposing ~30 device-emulation surfaces vs QEMU's hundreds → drastically reduced
  attack surface; KVM-based hardware isolation equivalent to full VMs (safeguard.sh).
- **Hard limits:** no GPU passthrough, no live migration, no arbitrary device attachment by design;
  persistent storage and full networking require you to build orchestration around it. "For most
  platform teams, running Firecracker directly means becoming a virtualization company" (edera.dev).
- Best used **through Kata** (Kata-on-Firecracker) rather than directly, unless you have a dedicated
  virtualization team.
- Snapshot/restore supports fast warm-pool spin-up (sub-100 ms class), useful for short-lived agent
  sandboxes.

### 1.5 Process sandboxes (bubblewrap / nsjail / firejail)

For **lightweight, in-container** confinement of semi-trusted agent tool calls:

- **bubblewrap (`bwrap`):** minimal, unprivileged, no daemon, no setuid on modern kernels; the engine
  behind Flatpak. Tiny, audit-friendly trusted base. No native cgroups — pair with
  `systemd-run --scope -p MemoryMax=… -p CPUQuota=…` for resource limits. Excellent filesystem-view
  control (`--ro-bind`, `--unshare-all`, `--die-with-parent`, `--new-session`).
- **nsjail:** Google-built, programmable (protobuf config + **kafel** seccomp policy language),
  `MODE_LISTEN` for per-connection network-service jails, native **cgroup v1/v2 + rlimit** support,
  fine-grained uid/gid mapping. The right tool for running actively-hostile code at scale
  (build farms, CTF, untrusted submissions). Startup < 5 ms.
- **firejail:** turnkey desktop sandbox, 1000+ shipped profiles, but **setuid-root by default** with a
  long historical local-privesc CVE list — prefer Flatpak/bubblewrap or firejail's non-setuid mode.

Common trap (2026): **unprivileged user-namespace restrictions break non-setuid bubblewrap/nsjail.**
Two causes — the legacy sysctls (`kernel.unprivileged_userns_clone=0`, `user.max_user_namespaces=0`)
and Ubuntu 24.04's `kernel.apparmor_restrict_unprivileged_userns=1` AppArmor clampdown — cause
sandboxes to half-start and fail on first mount/capability op. Must be tested on the real target distro.

### 1.6 Hardening primitives (defense-in-depth beyond the runtime choice)

Per Kubernetes Pod Security Standards "restricted" and vendor hardening guides, every production
agent container should set:

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  runAsGroup: 10001
  fsGroup: 10001
  seccompProfile: { type: RuntimeDefault }   # or Localhost custom profile
  containers:
    - name: agent
      securityContext:
        allowPrivilegeEscalation: false       # sets no_new_privs
        readOnlyRootFilesystem: true          # writable scratch via emptyDir/tmpfs
        capabilities: { drop: [ "ALL" ] }      # add back only what is strictly needed
```

- **Capabilities:** the runtime default set includes CHOWN, SETUID, SETGID, NET_RAW, KILL, etc. —
  most agent workloads need none. Drop ALL, add back only `NET_BIND_SERVICE` if binding <1024.
- **seccomp:** `RuntimeDefault` blocks ~44 dangerous syscalls (module loading, `ptrace`, raw mounts);
  never ship `Unconfined` in production. A Java/Python service needs <60 of the 400+ syscalls — a
  custom `Localhost` allowlist profile is the tightest option.
- **`allowPrivilegeEscalation: false`** blocks setuid-binary privilege gain; observable as
  `NoNewPrivs 1`.
- **`readOnlyRootFilesystem: true`** prevents dropping tools/modifying binaries; mount `emptyDir`
  (`sizeLimit`) or `tmpfs` at the paths that must be writable.

### 1.7 Rootless containers (user namespaces)

- **User namespaces** map container-UID 0 to an unprivileged host UID (e.g. 100000). Escape then lands
  as an unprivileged account — blast radius drops from "the whole machine" to "one powerless account"
  (bigiron.cc).
- Mapping is enforced by `/etc/subuid` + `/etc/subgid` allocations and the setuid helpers
  `newuidmap`/`newgidmap` (`uidmap` package); a setuid helper is precisely what prevents mapping
  container-root onto host-root.
- **Podman is rootless-native and daemonless** (no root-owned socket to attack); **Docker rootless**
  exists as opt-in, and rootful Docker offers the weaker `userns-remap` middle path.
- **Trade-off:** unprivileged user namespaces widen the kernel's unprivileged attack surface
  (privilege-escalation CVE history in overlayfs, nftables, etc.), which is why some hardened distros
  disable them.

## 2. Resource-Limit Strategies (cgroups v2)

**cgroups v2 unified hierarchy is the single enforcement layer** for all resource limits. A process
lives at exactly one node in one tree; controllers are enabled per subtree via `cgroup.subtree_control`
(a common failure: a child cannot set `memory.max` if the parent didn't enable `+memory`).

| Resource | Key files | Semantics |
|---|---|---|
| **CPU quota** | `cpu.max` = `"$QUOTA $PERIOD"` µs (default period 100000) | Hard bandwidth ceiling. `200000 100000` = 2 cores. Strictly enforced. |
| **CPU weight** | `cpu.weight` (1–10000, default 100) | Relative share under contention only. |
| **CPU burst** | `cpu.max.burst` | Allow temporary over-quota burst. |
| **CPU pinning** | `cpuset.cpus`, `cpuset.mems`, `cpuset.cpus.exclusive` | Static core/NUMA isolation. |
| **Memory hard** | `memory.max` | Exceeding → in-cgroup OOM kill (SIGKILL). The circuit-breaker limit. |
| **Memory soft** | `memory.high` | Reclaim/throttle, **no kill** — graceful degradation point. |
| **Memory protection** | `memory.low`, `memory.min` | Reclaim-order preferences / hard floor. Use `min` sparingly. |
| **Swap** | `memory.swap.max` | Per-cgroup swap cap; `= memory.max` disables swap. |
| **I/O** | `io.max` (`MAJ:MIN rbps= wbps= riops= wiops=`), `io.weight` | Per-device absolute/relative block-I/O limits (per-device only, not global). |
| **PIDs** | `pids.max` | Fork-bomb protection (cap process count). |
| **OOM grouping** | `memory.oom.group = 1` | Kill whole cgroup atomically instead of one process (avoids "zombie" half-broken containers). |
| **Pressure** | `cpu.pressure`, `memory.pressure`, `io.pressure` | **PSI** stall-time metrics (see §5). |
| **Events** | `memory.events` (`low/high/max/oom/oom_kill`) | Counters for alerting. |

**Recommended strategy (three-tier per agent):**

1. **Soft ceiling** `memory.high` ≈ 80% of budget → throttles instead of killing; gives early PSI signal.
2. **Hard ceiling** `memory.max` = 100% of budget → OOM kill as last resort.
3. **Absolute CPU/I/O caps** `cpu.max` / `io.max` → prevent noisy-neighbor starvation.
4. `pids.max` to bound process explosion; `memory.oom.group=1` for atomic cgroup OOM.
5. **Hierarchical quotas:** parent cgroup (e.g. `agent.slice`) holds the aggregate budget; child agent
   cgroups inherit limits via `cgroup.subtree_control` — giving a "tier budget" without per-agent caps
   interacting unpredictably.

**Critical pitfall:** `memory.max` without `memory.swap.max=0` on a swap-enabled host lets a leaking
process swap indefinitely before OOMing, masking the leak. Also note **`memory.high` throttling causes
severe latency / p99 spikes without any OOM or CPU increase** — a classic cgroup-v2 failure mode
(michal-drozd.com) — so `memory.high` must be monitored, not just `memory.max`.

**Network shaping:** cgroup v2 has no built-in bandwidth controller. The classic mechanisms are
`net_cls` (tags packets with a `classid`, consumed by `tc htb`) and `net_prio` (per-interface traffic
priority, cgroup-v1 controllers). On a modern cgroup-v2 host, network rate limiting is typically done
with **`tc` qdiscs on the veth** (e.g. TBF/HTB on the container interface) or CNI-level bandwidth
annotations, rather than cgroups. (Kernel `net_cls.rst`.)

## 3. Graceful Degradation & Circuit Breakers

**Reference implementation: Resilience4j** (Hystrix is end-of-life / maintenance mode). Patterns and
recommended starting configs:

| Pattern | Purpose | Starting config |
|---|---|---|
| **Timeout (TimeLimiter)** | Bound how long a call can hang; stop thread exhaustion | Per-endpoint, from the dependency's real SLA — not a blanket 30 s. `cancelRunningFuture: true` |
| **Circuit Breaker** | Fail fast when a dependency is unhealthy; give it room to recover | `slidingWindowSize ≥ 100`, `minimumNumberOfCalls ≥ 20`, `failureRateThreshold 50%`, `waitDurationInOpenState ≥ 30 s`, `permittedNumberOfCallsInHalfOpenState ≥ 3` |
| **Bulkhead** | Cap concurrent calls per dependency so one slow dependency can't monopolize resources | semaphore `maxConcurrentCalls` (e.g. 25) or thread-pool bulkhead; `maxWaitDuration` small |
| **Retry** | Absorb transient failures | `maxAttempts 3`, exponential backoff ×2 + **jitter**, restricted to idempotent ops and retryable exception classes; **ignore 4xx** |
| **Rate Limiter** | Protect a downstream/quota | `limitForPeriod` / `limitRefreshPeriod` |
| **Fallback** | Degraded-but-useful response | Serve stale cache / degraded mode |

**State machine:** CLOSED → (failure rate crosses threshold) → OPEN → (wait elapses) → HALF_OPEN →
(successes) → CLOSED, else re-OPEN. Failing fast in microseconds rather than after a 30 s timeout is
the whole point — it keeps resources free for traffic that can succeed.

**Decorator order matters.** Resilience4j's default aspect order outermost→innermost is
**Bulkhead → TimeLimiter → RateLimiter → CircuitBreaker → Retry**. Consequence: retries happen
*inside* the circuit breaker, so repeated failures still count toward tripping it, and an open breaker
does not fire retries. Keep this order unless you have a reason.

**Two high-severity pitfalls:**
- **Retry storm amplification:** 3 retries × 5 layers = **243×** load amplification during an outage,
  preventing recovery. Mitigate with a **token-bucket retry budget ≈10% of traffic** and full jitter.
- **Circuit-breaker thrashing:** tiny `slidingWindowSize`/`minimumNumberOfCalls` react to noise and
  cause immediate re-trip. Use larger windows and multiple half-open successes.

**Adapting to container runtimes:** the same patterns apply one layer down — a per-agent circuit
breaker keyed on health/latency, bulkhead pools per resource class (CPU/memory/IO/network), and a
degradation ladder: **full → throttled (memory.high/cpu.max pressure) → read-only → paused → terminated**.

## 4. Workspace Lifecycle Hardening

Agent workspaces need **atomic creation, guaranteed cleanup, and crash recovery**. Recommended patterns:

1. **Immutable / ephemeral-by-default workspaces:** base image is read-only; the agent writes only into
   a mounted scratch overlay. Recreate-from-base on failure is cheaper and safer than in-place repair.
   Persist only artifacts explicitly promoted out of the sandbox.
2. **Atomic creation with rollback:** allocate all resources (cgroup, user-ns mapping, network ns,
   volume) in a staging step and commit atomically; on any failure, tear down the partial allocation.
   Snapshot/fork (Firecracker snapshot-restore; overlayfs) gives fast, deterministic starts.
3. **Idempotent provisioning with convergence checks:** provisioning must be safe to re-run; validate
   desired state rather than assuming it.
4. **Guaranteed cleanup — reaper/finalizer pattern:** tie workspace lifetime to a parent (e.g.
   `bubblewrap --die-with-parent`, systemd scope, Kubernetes finalizer/ownerReference) so a crash of
   the launcher does not orphan containers, volumes, or networks. Add a periodic orphan reaper and a
   **force-cleanup timeout** for wedged teardowns. Orphaned compute is a real cost/leak failure mode.
5. **Crash recovery:** checkpoint/restore (CRIU, Firecracker snapshots) or simply recreate-from-base
   with an idempotent setup script; never assume graceful teardown happened.
6. **Ephemeral vs persistent:** ephemeral scratch (tmpfs/emptyDir with `sizeLimit`) for working state;
   durable named volumes/object storage only for outputs that must survive; sweep ephemeral storage on
   teardown.

## 5. Runtime Observability

### 5.1 Metrics — cgroup v2 / PSI / Prometheus

- Export per-cgroup counters from `memory.events` → `cgroup_memory_events_total{event="high|max|oom_kill"}`,
  and PSI from `cpu.pressure` / `memory.pressure` / `io.pressure` →
  `cgroup_pressure_seconds_total{resource="cpu|memory|io"}`.
- **PSI is the correct "approaching saturation" signal** — it measures stall time and fires *before*
  any hard limit is hit, catching contention that utilization dashboards miss.
- **Kubernetes v1.36 graduated PSI metrics to GA** (`KubeletPSI` gate locked on): kubelet exports
  `.cpu.psi/.memory.psi/.io.psi` at node, pod, and container granularity; Prometheus via
  `/metrics/cadvisor`: `container_pressure_{cpu,memory,io}_waiting_seconds_total`. Node requirements:
  kernel ≥ 4.20, **cgroup v2**, `CONFIG_PSI=y`, Linux-only.
- **Alerting guidance:** `memory.high` rate > 0 sustained (early warning), any `oom_kill` (incident),
  **any sustained non-zero `memory.full`** PSI (paging incident in progress), rising
  `container_pressure_*_waiting_seconds_total` on a container whose usage is flat (noisy neighbor).

### 5.2 Tracing — OpenTelemetry

- Deploy the **OTel Collector** as a **DaemonSet** (per-node: OTLP receiver for apps, `k8sattributes`
  processor to attach pod/namespace/node metadata, `kubeletstats` receiver for pod/container metrics,
  `filelog` receiver for stdout/stderr) plus a single-replica **Deployment** (k8sclusterreceiver,
  k8sobjectsreceiver for events).
- **`k8sattributes` processor is essential** — it correlates app traces/metrics/logs with K8s metadata;
  requires a ClusterRole for the collector's service account.
- Lower-level container-runtime tracing: containerd exposes OTel tracing via plugin (v1.6+); CRI-O
  supports it since v1.23; the Rust `conmon-rs` adds deep runtime spans; `runc`/`crun` have **no** OTel
  support. Kubelet tracing (`KubeletTracing` gate) links kubelet↔CRI gRPC calls. There is a real
  overhead cost — budget for it.
- **Prometheus ingestion:** Prometheus can receive OTLP (`--web.enable-otlp-receiver`); promote key
  resource attributes (`service.name`, `k8s.pod.name`, `container.name`) so OTel metrics are usable in
  PromQL.

### 5.3 eBPF runtime security — Cilium Tetragon

- **Tetragon** provides eBPF-based security observability **and runtime enforcement**, Kubernetes-aware
  (namespaces/pods). It filters in-kernel, so overhead is low and hooks run where userspace can't
  tamper with the data.
- Detects process-exec, syscall, and I/O events; can **follow child processes** (lineage) to detect a
  container escape where a process spawns in one namespace and acts in another; can **kill a process
  before a syscall completes** (e.g. on privilege change).
- Recommended posture: **observe first** to learn the agent workload's expected behavior, then author
  least-privilege enforcement policies (and seccomp allowlists) from observed behavior rather than
  guesswork.
- `bpftrace` is complementary for ad-hoc kernel tracing/debugging.

### 5.4 Logging

Structured JSON to stdout/stderr, collected by the OTel `filelog` receiver → Loki/Elasticsearch; never
parse logs to correlate — use trace IDs and resource attributes to join signals.

## 6. Recommended Technology Stack (with justification)

**Recommended stack — a tiered, defense-in-depth model:**

| Layer | Recommendation | Justification |
|---|---|---|
| **Baseline (everywhere)** | **cgroup v2** enforcement + **rootless** containers + restricted `securityContext` (drop ALL caps, `RuntimeDefault` seccomp, `runAsNonRoot`, `readOnlyRootFilesystem`, `no_new_privs`) + `bubblewrap`/`nsjail` inner sandbox | Works on any modern Linux; no KVM needed; strongest cost/benefit baseline; the inner sandbox is a second barrier inside the container |
| **Default isolation for untrusted agent code** | **gVisor (`runsc`)** via `RuntimeClass` | Userspace-kernel syscall boundary without KVM (deployable in nested-virt/CI); moderate overhead; strong syscall restriction. Fall back to Kata for incompatible syscalls |
| **High-isolation tier (adversarial / multi-tenant)** | **Kata Containers on Firecracker** via `RuntimeClass` | Hardware (KVM) boundary, tiny VMM attack surface, I/O near-native; use where KVM is present |
| **Resource management** | cgroup v2 unified hierarchy, three-tier (`memory.high`/`memory.max` + `cpu.max`/`io.max`/`pids.max`/`memory.oom.group`) | Single consistent enforcement layer; soft-then-hard degradation |
| **Resilience** | **Resilience4j**-style composition: Timeout → Bulkhead → CB → Retry(budget+jitter) → Fallback, plus a per-agent degradation ladder | Proven, configurable, observable; retry budget prevents storms |
| **Workspace lifecycle** | Immutable base + ephemeral scratch + atomic create/rollback + reaper/finalizer cleanup | Cost/leak control; deterministic recovery |
| **Observability** | **OpenTelemetry** collector (DaemonSet + Deployment) → Prometheus (OTLP ingest) + Tempo/Jaeger + Loki; **PSI** + `memory.events` alerting; **Cilium Tetragon** for runtime security | Vendor-neutral, correlates all signals with K8s metadata; PSI catches contention before OOM; Tetragon enforces least privilege |

**Decision rule:** isolation tier is selected per agent/workload class via `RuntimeClass`:
- Trusted, internal tooling → baseline container + inner sandbox.
- Untrusted/LLM-written code, no KVM available → **gVisor**.
- Untrusted/adversarial, multi-tenant, KVM available → **Kata-on-Firecracker**.

## 7. Risk Assessment (per approach)

| # | Approach | Risk | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Plain `runc` containers | Shared host kernel; escape = host compromise | Critical | Never the sole boundary for untrusted code; add gVisor/Kata + inner sandbox |
| R2 | gVisor | Syscall compatibility gaps (io_uring, eBPF, exotic ioctls) break agent toolchains | High | Test real workloads against gVisor compat matrix; fall back to Kata tier |
| R3 | Kata / Firecracker | Requires KVM; unavailable in nested-virt / some clouds | Medium | Detect `/dev/kvm`; default to gVisor where absent |
| R4 | MicroVM overhead | 20–180 MB/VM reduces density for many short-lived sandboxes | Medium | Firecracker snapshot warm-pool; right-size per class |
| R5 | Process sandboxes alone | Share host kernel; not a VM boundary | High | Layer inside a container/VM; pair bubblewrap with `systemd-run` cgroups |
| R6 | Unprivileged user namespaces | Widened kernel unprivileged attack surface; CVE history | High | Patch kernel; consider disabling userns on untrusted multi-tenant hosts; rootless where risk accepted |
| R7 | 2026 userns restrictions | Ubuntu 24.04 AppArmor / sysctls break non-setuid bwrap/nsjail | Medium | Test on target distro; ship AppArmor `userns,` profile or setuid fallback |
| R8 | cgroup misconfig | `memory.max` without `swap.max=0` masks leaks; missing `subtree_control` silently fails | High | Explicit swap cap; verify writes; bake limits into unit/scope definitions |
| R9 | `memory.high` throttling | Latency/p99 spikes with no OOM or CPU signal | High | Monitor `memory.events{high}` + PSI; set `high`≈80% of `max`; alert on PSI |
| R10 | Network shaping | cgroup v2 has no bandwidth controller | Medium | Use `tc` qdisc on veth / CNI bandwidth annotations; `net_cls`+`tc` on legacy |
| R11 | Retry storms | 10–100× load amplification during outage | Critical | Token-bucket retry budget ≈10%; full jitter; retry idempotent only |
| R12 | CB thrashing | Small windows cause immediate re-trip, slow recovery | High | `slidingWindowSize ≥ 100`, `minimumNumberOfCalls ≥ 20`, ≥30 s open, ≥3 half-open successes |
| R13 | Orphaned workspaces | Leaked containers/volumes/networks → cost + exhaustion | High | Reaper/finalizer, `--die-with-parent`, force-cleanup timeout, periodic sweep |
| R14 | Observability gaps | Missed contention/OOM; no cross-signal correlation | Medium | OTel from day one; PSI + `memory.events` alerts; CB-state/retry-budget alerts |
