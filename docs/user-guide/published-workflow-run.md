# Редактор → сохранённая версия → запуск (без локального live-теста)

Сценарий: **Редактор** → указать имя → разместить линейный граф Start → (Agent → Gate)+ → End → для каждого Agent выбрать реальные UUID определения агента, model profile и tool policy → для Gate выбрать `automatic` и действительный UUID контракта → **Проверить** → **Сохранить черновик** → **Опубликовать версию** → выбрать проект → **Запустить версию** → **Запуски**.

При запуске не отправляется произвольный список задач из браузера. Orchestration-server получает ID опубликованной неизменяемой версии, **повторно компилирует** сохранённый snapshot и создаёт задачи в штатном engine, сохраняя графовый node_id, связи depends_on и contract_id от следующего автоматического Gate. Runtime проводит настоящую Contract Gate проверку; независимая QA и human release approval остаются независимыми серверными условиями.

**Проверка канонического JSON:** сервер и редактор требуют `schema_version: "1.0"`, `metadata` с названием, целочисленной версией и timestamp с часовым поясом, а также `nodes` и `edges` с полным набором обязательных полей. Позиции нод должны иметь конечные числовые `x/y`; настройки рёбер — правильные типы; неизвестные top-level, node и edge свойства не принимаются. Даже пустое `edge.condition: ""` не является исполняемой семантикой и блокирует запуск. Невалидный опубликованный или архивный снимок не создаёт задач: preflight блокируется, а launch возвращает ошибку. В редакторе подсказки и предварительная компиляция используют одну и ту же JSON Schema-проверку; сервер повторно валидирует свой неизменяемый snapshot.

**Поддержано сейчас:** ровно один Start, ровно один End, последовательные Agent + automatic Gate. **Не поддержано и явно блокируется:** condition, parallel/join, human_approval как графовая операция, tool, memory, delay, ветви, циклы, output_mapping, edge condition, retry/skip и manual Gate. Их можно использовать как draft-элементы, но **не** опубликовать как исполняемый workflow. Неправильные UUID агентных ссылок или контрактов также блокируют публикацию. Browser preflight — подсказка; единственное авторитетное решение принадлежит backend.

**Граница профилей (#254):** ссылки на AgentDefinition/ModelProfile/ToolPolicy сохраняются как **provenance** в input_data задачи и пока не гарантируют, что native worker фактически применит модель, prompt, scopes или бюджет. За это отвечает будущая интеграция dispatch. Наличие опубликованной версии и созданного run не доказывает платный OpenRouter вызов или полный семистадийный SDLC.

Черновик хранится в backend, версии неизменяемы; обновления используют expected_version и отказ 409 при гонке. Опубликовать версию можно только если snapshot соответствует сохранённому черновику. Импорт JSON не перезаписывает текущую server definition: он открывается как новый черновик, а перед заменой несохранённой работы требуется подтверждение. Экспорт сохраняет локальный JSON. Запуск может включить платный worker и поэтому требует отдельного подтверждения пользователя.

**Приёмка для закрытия #253:** живой Chromium/Compose, версии после restart, полное соответствие node/contract/task/log, QA/release proof, реальная проверка профилей и независимых разрешений. CI и ASGI HTTP-тесты — необходимые, но не достаточные доказательства live-готовности.

Для Gate есть каталог существующих контрактов из backend с фильтрацией по выбранному проекту и действие «Создать Contract Gate summary». Созданный контракт сразу подставляется в конфигурацию выбранного Gate. Это отдельная явная запись сервера; создание контракта само по себе не запускает агент.

Инспектор версии позволяет выбрать старый опубликованный снимок и запустить именно его — даже если текущий черновик уже изменён. Перед запуском обязательно показывается номер версии и подтверждение потенциально платных запросов. Сервер никогда не компилирует изменяемый draft при таком запуске.

## Переключение контекста проекта и запуска

Выбор другого проекта (или снятие выбора проекта) атомарно снимает выделение предыдущего запуска и задачи: карточка, журнал и сведения из старого проекта не сохраняются как текущие. При переключении запуска выбор задачи сбрасывается, а детали и задачи предыдущего запуска не показываются, пока загружается новый. Повторный выбор того же проекта/запуска сохраняет текущий контекст и не обнуляет историю. Списки «Запуски» и «Живой журнал» в выбранном проекте фильтруются по нему даже при ответах от ранее начатых HTTP-запросов. Это клиентская защита от ошибочного контекста, не замена серверным RBAC и разграничению доступа.

Раздел «Конвейер и роли» использует ту же область: предлагает только запуски выбранного проекта, читает все страницы списка, проверяет принадлежность запусков даже при ошибочном серверном фильтре и не показывает задачи прежнего запуска, пока новый ответ загружается. Роли агентов отображаются отдельно; переключение проекта не выдаёт разрешений на просмотр чужих данных и не заменяет серверную авторизацию.

Kanban-доска проверяет принадлежность каждого показываемого запуска текущему проекту непосредственно при отрисовке, даже если предыдущий HTTP-ответ ещё находится в памяти. Список запусков и счётчик используют одинаковую область. Повторный выбор того же проекта на доске не сбрасывает запуск или задачу; смена проекта сбрасывает оба выбора атомарно через общее состояние навигации.

## Безопасное отображение данных задачи и попыток (#256)

«Карточка задачи», «Запуски», Kanban, «Конвейер» и операторский «Карантин / восстановление» показывают серверные результаты и сведения о заданиях только в режиме чтения. Текст ошибок worker, заголовки/описания, пути Git-артефактов и вложенные JSON `input_data`/`output_data` перед выводом проходят redaction: известные поля `api_key`, `authorization`, `password`, `client_secret`, `private_key`, `*Token` и т. п. заменяются на `[REDACTED]`; query-параметры URL удаляются. Длинные/слишком глубокие структуры ограничиваются при отображении. Полезные не-секретные поля, такие как статус и `token_usage`, остаются доступными.

Это **дополнительная защита только на экране**, а не API redaction, очистка базы данных или серверная авторизация: браузер уже получил ответ backend, и доступ к исходному сетевому payload определяется серверным RBAC. Нельзя помещать настоящие секреты в task input/output, agent errors, Git paths, QA evidence или журналы. При подозрении на утечку отозвать/заменить ключ и удалить источник по утверждённой процедуре. Отображаемые worker-артефакты не становятся независимо подтверждёнными только от того, что их строки санитизированы.

## Run-centric запуск: границы подтверждения и диагностика сбоев (#256)

В разделе **Запуски** выберите проект, опубликованный workflow и
неизменяемую версию; нажмите «Проверить готовность запуска». Предварительная
проверка привязана к **точной тройке** `project/definition/version`.
Запоздавший ответ preflight после смены выбора не активирует кнопку запуска.
Перед созданием run API проверяется снова, затем пользователь отдельно
подтверждает возможность платных вызовов.

**Успех `POST .../runs` означает, что run создан сервером**, но не
что worker начал работать или QA пройдена. UI немедленно показывает
серверный ID и открывает карточку созданного run. Последующие GET
сведений о run и задачах обновляют панели независимо; их ошибки **не**
превращают успешный POST в «запуск не выполнен». Для диагностики
недоступных сведений используйте «Обновить» и сохранённый ID. При
неопределённом результате самого POST (например, обрыв соединения) сперва
проверьте серверную историю запусков, **не нажимайте повторно**, пока
не исключите уже выполненный side effect. Внешняя идемпотентность POST
не доказана данным UI-исправлением.

После создания можно перейти в карточку задачи (только чтение),
журнал и карантин. Contract Gate, независимая QA, Git evidence и
human release approval остаются авторитетными серверными условиями;
отсутствующий worker или провайдер не даёт оснований показывать
автономное исполнение как завершённое.

Автоматические evidence: frontend `RunsSection.launch.test.tsx` проверяет
успешный POST при ошибке следующих GET и отклонение старого preflight;
Compose/Chromium `compose-acceptance.spec.ts` проверяет второй запуск
из раздела «Запуски» той же опубликованной версии, серверное сохранение
задач и появление после reload, без оплачиваемых completions.


## Безопасный повтор запуска: атомарная идемпотентность PublishedRun

В **Запусках** и **Редакторе** браузер создаёт криптографически случайный
`idempotency_key` для каждой *намеренно новой* публикационной операции.
Ключ сохраняется в состоянии страницы, пока сервер не вернул подтверждённый
`run.id`. Если ответ `POST` потерян, повторное подтверждение той же
версии отправляет **тот же** ключ, а не создаёт вторую задачу и возможные
платные вызовы. После подтверждённого запуска следующая намеренная
операция получает новый ключ. Неподтверждённые ключи для каждой выбранной
тройки project/definition/version сохраняются в общем состоянии и
`sessionStorage` **только текущей вкладки**: переход между разделами или
reload не делает следующий запуск новым. Очистка данных вкладки, другой
браузер, private browsing без хранения или смена аутентифицированного
субъекта не позволяют автоматически восстановить такой ключ. В этих
случаях прежде проверьте серверный список запусков, не запускайте снова
вслепую. Неподтверждённый ключ не даёт права выполнить новую операцию:
сервер привязывает его к текущему субъекту и проверяет preflight при
отсутствии уже сохранённого receipt.

Сервер сопоставляет ключ с субъектом аутентификации и каноническим
отпечатком запроса (workflow, immutable version, project, workspace, name,
input). В базе хранится только SHA-256 от ключа/субъекта и отпечатка,
**не сырое значение ключа и не credentials**. Запись об идемпотентности
и run/tasks/events сохраняются **в одной транзакции**. Повтор того же
запроса возвращает тот же ID и не создаёт новых задач. Повтор того
же ключа с другим payload/версией отклоняется с HTTP 409; новая
намеренная операция с новым ключом создаёт новый run.

Данный контракт действует **только** на
`POST /api/v1/workflows/definitions/{definition_id}/versions/{version_id}/runs`.
Старые клиенты без ключа продолжают создавать отдельный run на каждый
успешный POST. Универсальный `POST /workflows/runs` и прямой worker
claim **не приобретают** неявную идемпотентность.

В существующей SQLite-БД таблица `published_run_requests`
создаётся штатным `Base.metadata.create_all` при запуске обновлённого
orchestration-server. Не удаляйте её и не очищайте вручную, пока остаются
подтверждённые run или возможны повторные вызовы клиента. Перед
обновлением сделайте резервную копию; при откате ПО нельзя принимать
старый endpoint как обеспечивающий exactly-once. Это гарантия
**однократного создания run**, а не exactly-once выполнения внешних
инструментов или платных запросов worker: lease/ledger/reconciliation
по-прежнему обязательны.

Проверка: `test_published_graph_runs.py` включает повтор с тем же
ключом, конфликт изменённого тела, отдельный намеренный запуск,
некорректные ключи и рестарт control plane; frontend
`RunsSection.launch.test.tsx` фиксирует тот же ключ после
неопределённого сетевого ответа и новый ключ после подтверждения.


### Смена проекта во время редактирования

Редактор сохраняет несохранённый документ на экране, если выбран другой проект, но **не перепривязывает** к новому проекту чужой workflow. Сохранение, публикация и запуск блокируются до явного создания нового черновика, импорта JSON или открытия workflow текущего проекта. При необходимости сначала экспортируйте несохранённый граф в JSON. Ответы старых запросов списка/open/preflight больше не могут подменить новый контекст или запустить старую версию. Локальные изменения, внесённые во время сохранения по HTTP, остаются несохранёнными, а не обозначаются как уже записанные на сервере. Регрессионные тесты включают переключение проекта во время загрузки, открытия, сохранения и preflight.


### Повторное открытие редактора после навигации

Если перейти из редактора в другой раздел и затем вернуться, несохранённый граф остаётся в памяти вкладки. Его исходный проект и идентификатор сохранённого workflow сохраняются вместе с документом: смена проекта не может автоматически присвоить его новому проекту. После возврата к уже сохранённому графу в **том же** проекте необходимо открыть его из списка workflow, чтобы восстановить актуальную серверную ревизию и избежать дублирующего создания при сохранении. Любой неподтверждённый черновик можно предварительно экспортировать в JSON. Проверка включает новый Chromium/Compose сценарий с реальными HTTP POST/GET двух проектов; платные completions не вызываются.


### Достоверность справочников в инспекторе нод

В поле выбора Contract Gate отображаются только глобальные или принадлежащие текущему проекту контракты. После смены проекта/узла/адаптера или размонтирования инспектора ответы старых запросов не выбирают контракт и не могут изменить другую ноду; серверный ответ с несовпадающим `project_id` отклоняется. Списки профилей агентов, моделей и инструментальных политик загружаются полностью по серверным `next_cursor` с ограничением числа страниц. Повторяющийся/неверный курсор или ошибка загрузки блокируют использование частично полученного списка, вместо сокрытия поздних профилей. Это не заменяет проверку references при серверном preflight — публикация и запуск по-прежнему имеют отдельные серверные ограничения.


### Смена проекта и навигация во время запуска из раздела «Запуски»

Preflight привязан к конкретному API, проекту, definition, immutable version и поколению выбора. Возврат к той же версии через другой выбор (A → B → A) **не** делает ранее полученный ответ актуальным. Несоответствие ID версии/definition в ответе backend приводит к отказу. При смене выбора старый preflight не открывает кнопку запуска, а ожидание запроса не блокирует новую страницу.

Если подтверждённый пользователем HTTP POST уже отправлен и проект сменился либо раздел «Запуски» закрыт, поздний ответ **не** переводит интерфейс в чужой run и не меняет выбор пользователя. При достоверном ответе `run.id` и совпадающем `project_id` ранее выданный идемпотентный ключ удаляется из списка неопределённых запросов даже после ухода со страницы. Такой run можно открыть позднее из истории его исходного проекта. Если POST завершился неопределённо, ключ сохраняется для безопасного повтора того же запроса; не инициируйте новый запуск вслепую. Проверки включают задержанный preflight, задержанный подтверждённый POST после смены проекта и после размонтирования раздела, недостоверный ответ preflight и замену API при неизменных ID.


#### Реальная браузерная проверка переключения проекта и двух типов ответа POST

Compose/Chromium acceptance содержит сценарий `real Compose run POST remains project-scoped after delayed reply, lost reply and recovery`: через настоящий backend создаются два проекта, profile/model/policy, Contract Gate и опубликованный исполняемый граф. Первая операция POST **действительно сохраняет** run и одну задачу в серверной БД, но доставка ответа браузеру задерживается до переключения проекта. Новый проект не выбирает старый run; после возврата run остаётся доступным из истории исходного проекта. Вторая, явно подтверждённая операция сохраняется на сервере, но её ответ умышленно теряется на транспортном уровне: после переключения проекта, полной перезагрузки страницы и возврата исходный ключ используется повторно, а сервер возвращает тот же ID, не создавая дубликат. Проверяются сохранённый immutable version ID, node/contract и отсутствие запросов AI-completions. Это транспортная симуляция при **реальном** API и persistence, но не доказательство фактической live-работы провайдера или выпуска.


### Живой журнал: безопасная пауза, полнота списка и изоляция проекта

**«Пауза» действительно отключает WebSocket/SSE**, не просто прячет новые строки при продолжающемся потоке. При возобновлении создаётся новое соединение, а запрос `after` начинается с последнего **показанного** server event ID; события, записанные сервером во время паузы, догружаются через его событийную историю в пределах доступного retention. Это не обещание бесконечного хранения событий: если сервер удалил старые события, восстановить их уже нельзя. В polling-режиме пауза приостанавливает опрос; восстановление показывает текущее состояние снимка, а не все промежуточные переходы. Значок прямо отличает паузу, настоящий live stream и fallback-опрос.

Каталог запусков журнала теперь читает все страницы server cursor (защитный предел 100 страниц), отображает только запуски текущего проекта и отвергает некорректную/циклическую пагинацию вместо ложного пустого списка. При выбранном проекте журнал **не открывает WS/SSE и не опрашивает snapshot**, пока серверный каталог не подтвердил принадлежность run. Смена API, проекта или запуска очищает старые события и курсор; запоздавший каталог не даёт доступ к прошлому контексту. Одновременно может выполняться только один snapshot GET, чтобы медленный ответ не откатывал журнал. Реальный Compose/Chromium acceptance проверяет паузу, возобновление и сохранение server event; unit tests — догрузку пропущенных событий, поздние страницы, неправильный project ID, циклический курсор и запоздавший ответ старого проекта. Это дополнительные frontend fences, а не замена backend RBAC.


### Карточка задачи: серверная принадлежность и достоверность evidence

До загрузки attempt/Git/QA-отчётов карточка читает задачу и её запуск через два отдельных backend API и проверяет, что task ID, `workflow_run_id`, выбранный run ID (если выбран) и текущий project ID согласованы. Если сервер недоступен или ID противоречат друг другу, **не открываются** дополнительные запросы доказательств, не показываются результаты бывшего проекта, доступны лишь предупреждение и повторная проверка. При смене задачи, проекта, run или API-адаптера старое подтверждение сразу недействительно, включая A → B → A; обновление перечитывает серверную принадлежность перед всеми другими данными.

История попыток и worker-reported Git-отчёты должны содержать ID именно текущей задачи; некорректные или чужие записи скрываются целиком, а не попадают в карточку как достоверные. Даже корректно привязанный Git SHA от worker не приравнивается к независимой Git/QA verification. Положительная строка «QA подтверждена» допустима только при `task_id` текущей задачи, 40-символьном commit SHA, непустом подписанте и всех трёх tester/reviewer/security gate run IDs; один лишь `status=verified` не является достаточным. Неверные, недоступные или неполные receipts получают явно непроверенный статус. Эти правила общие с read-only сводкой запуска. После обновления карточка заново устанавливает принадлежность и исключает старый положительный статус до новых ответов. Проверки охватывают изменённый проект, чужой ответ run, QA/Git/attempt mismatch, задержанный старый GET, непрямой переход и полный browser/Compose UI→task evidence путь без платного AI.


### Достоверность полной истории запуска

При смене выбранного проекта или API-адаптера весь state раздела «Запуски» уничтожается вместе со старыми асинхронными ответами, preflight и QA-подтверждениями. Это также относится к быстрому переключению A → B → A с тем же ID запуска. Серверная страница задач перед показом проверяется целиком: все `workflow_run_id` должны принадлежать запрошенному запуску, каждый task ID должен быть валидным и встречаться только один раз. Нельзя скрыть чужую строку фильтром и считать остаток списка полным. При ошибке или повторяющихся ID **история, прогресс и агрегат QA не подтверждены**; вместо успешных статусов показывается причина и предлагается повторить чтение. Отдельная сводка запуска использует те же ограничения, даже если её вызывает иной UI. Это дополнительная клиентская проверка поверх backend RBAC, а не его замена.


### Безопасный запуск непосредственно из редактора

Кнопка «Запустить» редактора использует **ровно опубликованный immutable workflow**, а не изменённый локальный черновик. После нового серверного preflight она дополнительно проверяет, что ответ относится к запрошенным `workflow_definition_id` и `workflow_version_id`. Перед первым POST необходим явный операторский confirm с предупреждением о возможных платных вызовах.

Ответ HTTP 2xx **не считается подтверждением запуска**, если отсутствуют корректный run ID, исходный `project_id` или provenance (`input_data._workflow_definition_id`, `input_data._workflow_version_id`) для выбранного snapshot. При несовпадении клиент не переходит в чужой run и не удаляет существующий ключ: результат POST признаётся неопределённым и требует проверки истории/безопасного replay. При потере HTTP-ответа сохранённый ключ идемпотентности переживает закрытие редактора, возврат и перезагрузку страницы; повтор на той же опубликованной версии передаёт исходный ключ, а backend проверяет receipt, не создавая двойной run. Подтверждённый сервером корректный POST снимает исходный ключ даже после смены проекта или ухода со страницы, **но никогда не переключает текущий проект на старый run**. Это та же гарантия, что у кнопки запуска в разделе «Запуски», с дополнительной проверкой опубликованного provenance. Клиентское восстановление не заменяет server idempotency, preflight, RBAC или live операторскую приёмку.
